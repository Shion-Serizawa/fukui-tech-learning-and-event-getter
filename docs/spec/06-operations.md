# 06. 運用

## 環境

本番ひとつ（Q9=A）。ステージング環境は作らない。承認の仕組みは「PR の CI」と「骨格の受け入れ確認」が担う。

## ローカル開発

```sh
mise install                 # Node（mise.toml で固定）
npm ci
cp .dev.vars.example .dev.vars   # 値を入れる。コミットしない
npm run db:migrate:local
npm run dev                  # Worker。--test-scheduled 付き
#   別端末で: curl "http://localhost:8787/__scheduled?cron=17+*+*+*+*"  → 収集を1回起動
npm run dev:web              # Pages（公開一覧）
npm run check                # 型・lint・整形・テスト（カバレッジ込み）・仕様との対応
```

ローカルの `npm run dev` で収集を起動すると、`.dev.vars` のキーで**本物の connpass API を呼ぶ**（1回の収集で数リクエスト、1100ms 間隔）。何度も連打しない。日常の確認は自動テスト（偽の fetch + フィクスチャ。外部通信は遮断されている）で行う。

## シークレット

値は書かない。名前だけを書く。

| 名前                    | 置き場所                                                               | 用途                                                                                                                                |
| ----------------------- | ---------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------- |
| `CONNPASS_API_KEY`      | Worker のシークレット（`wrangler secret put`）、ローカルは `.dev.vars` | connpass API の認証（C-03）。**1つしか発行されず、漏れても自分で再発行できない**ので厚く守る                                        |
| `DISCORD_WEBHOOK_URL`   | Worker のシークレット、ローカルは `.dev.vars`（空なら送らない）        | 停止・復旧の通知（HLT-05）。URL を知っていれば誰でも投稿できるので、値をどこにも書かない。漏れたら Discord 側で Webhook を作り直す  |
| `CLOUDFLARE_API_TOKEN`  | GitHub Actions のシークレット（デプロイ用ワークフローのみが参照）      | デプロイ。スコープ付きトークン（Workers Scripts:Edit / D1:Edit / Pages:Edit を対象アカウントに限定）。**Global API Key は使わない** |
| `CLOUDFLARE_ACCOUNT_ID` | GitHub Actions の変数                                                  | デプロイ                                                                                                                            |

`wrangler.jsonc` の `vars` は平文の設定であってシークレットではない。シークレットを `vars` に書かない。

## リポジトリの初期設定（手作業）

ひとしきりのセットアップが終わった時点で GitHub の公開リポジトリを作り、次を設定する（team.md「Way of Working」）。

- [ ] `main` のブランチ保護: PR 必須、ステータスチェック必須（`型・リント・整形・テスト・ビルド`、`シークレット検出`）、承認者は不要
- [ ] シークレットスキャンとプッシュ保護を有効にする
- [ ] Dependabot を有効にする（設定は `.github/dependabot.yml`）
- [ ] CodeQL を有効にしてよい（表示のみ。ゲートにしない）

## CI

`.github/workflows/ci.yml`。PR と `main` への push で動く。

| ジョブ                           | 止めるか | 内容                                                                                                         |
| -------------------------------- | -------- | ------------------------------------------------------------------------------------------------------------ |
| 型・リント・整形・テスト・ビルド | 止める   | `typecheck` → `lint` → `fmt:check` → `types:check` → `test:coverage`（行 80%）→ `spec:check` → `build:check` |
| シークレット検出                 | 止める   | gitleaks（履歴全体）                                                                                         |
| 依存の脆弱性                     | 表示のみ | `npm audit`                                                                                                  |

止めるものを絞るのは意図的。単独開発でゲートを増やすと、止まった理由が本物かを毎回1人で判断することになり、閾値をいじって黙らせる習慣がつく。

## デプロイ

**未作成**。骨格（収集 + 保存）の実装と一緒に作る。決まっていること:

- 別ワークフロー `.github/workflows/deploy.yml`。`on: push` の `main` のみで動く。`pull_request` では動かない
- CI のジョブが通った後に、Worker（`wrangler deploy`）→ D1 マイグレーション（`wrangler d1 migrations apply --remote`）→ Pages（`wrangler pages deploy`）の順
- 初回は手で D1 を作り（`wrangler d1 create hokuriku-it-events`）、`database_id` を `wrangler.jsonc` と `web/wrangler.jsonc` に書く（ID はシークレットではない）

### デプロイ後の確認

- 公開ページが 200 を返し、フッターに最終収集日時が出る（WEB-10）
- Cron は次の起動（毎時17分）を待つ必要があるので、デプロイ直後の確認には含めない。次の17分過ぎに最終収集日時が更新されることを見る

### ロールバック

| 対象   | 手順                                                                                   |
| ------ | -------------------------------------------------------------------------------------- |
| Worker | `wrangler rollback`（直前のデプロイへ戻す）                                            |
| Pages  | ダッシュボードから以前のデプロイを再公開する                                           |
| D1     | スキーマ変更は列の追加のみ（04-data.md）なので、コードだけ戻せばよい。データは戻さない |

## 無料枠の見積もり（C-09）

| 資源               | 使用量の見積もり                                           | 無料枠に対して                      |
| ------------------ | ---------------------------------------------------------- | ----------------------------------- |
| Worker の起動      | Cron 24回/日 + RSS リーダーの取得（多くて数百回/日）       | 10万リクエスト/日に対して十分小さい |
| Worker の CPU 時間 | 収集1回は待機が大半で、CPU は数十 ms 程度の見込み          | 実測で確認する                      |
| D1 の行の読み書き  | 収集1回で数十〜数百行の書き込み、表示1回で数百行の読み取り | 十分小さい                          |
| D1 の容量          | 30日より古いものを消す（STO-06）ので数千行程度             | 十分小さい                          |
| Pages              | 静的ファイル + Functions の呼び出し                        | 十分小さい                          |

構成を変えるときはこの表を更新する。具体的な上限値は Cloudflare の公式ドキュメントで確認すること（変わることがある）。

## 実レスポンスとの突き合わせ（V-nn）

**API キーは発行済み。実装の最初（骨格の着手前）にこれを行う。** 自動テストからではなく**手で1回だけ**実レスポンスを取得し、次を確かめる。取得した生のレスポンスはリポジトリの外（例: `/tmp`）に置き、確認が済んだら消す（主催者名が含まれるため）。

```sh
# 例: 福井・今月分を1回だけ。キーはシェルの履歴に残さないよう .dev.vars から読む
set -a; . ./.dev.vars; set +a
curl -sS -H "X-API-Key: $CONNPASS_API_KEY" \
  "https://connpass.com/api/v2/events/?prefecture=fukui&ym=$(date +%Y%m)&count=100" > /tmp/connpass-sample.json
```

| ID   | 確かめること                                                                                         | 違っていたら                                                                              |
| ---- | ---------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------- |
| V-01 | レスポンスのフィールド名・型・null の有無が 04-data.md の表と一致するか                              | フィクスチャと検証（`src/connpass/`）を直す。必須・任意の区分を見直す                     |
| V-02 | レート制限の公式の値（C-04、A-01）。公式リファレンス（https://connpass.com/about/api/v2/）で確認する | COL-05 の間隔と C-04 を更新する                                                           |
| V-03 | `ym` に複数の月をカンマ区切りで渡せるか。上限はあるか                                                | COL-03 を、月ごとに分けて問い合わせる方式に変える（リクエスト数とレート制限を再計算する） |
| V-04 | `prefecture` に `fukui` 等を1つ渡して、その県のイベントだけが返るか                                  | COL-02 を直す                                                                             |
| V-05 | `start` が1始まりか、`results_available` の意味（全件数か）                                          | COL-04 を直す                                                                             |
| V-06 | 北陸3県で実際に何件返るか。都道府県の設定漏れでの取りこぼしがどの程度か（A-05）                      | 許容範囲を超えるなら、取りこぼしの補正を別途検討する（D-11）                              |
| V-07 | API 利用申請で申告した利用目的に、公開の RSS が含まれるか（R-07、C-07）                              | 含まれなければ connpass に利用目的の追加を届け出るか、RSS を公開しない形に戻す            |

確認が済んだら、フィクスチャを実データの形に合わせて**手で**書き直す（実レスポンスをそのままコミットしない）。

## M-02 の測り方

D1 に対して（`wrangler d1 execute hokuriku-it-events --remote --command "..."`）:

```sql
SELECT
  COUNT(*) AS total,
  SUM(CASE WHEN first_seen_at < started_at THEN 1 ELSE 0 END) AS delivered_before_start
FROM events
WHERE ended_at <= :now AND ended_at > :now - 14 * 24 * 60 * 60 * 1000;
```

`delivered_before_start / total` が 100% であること。
