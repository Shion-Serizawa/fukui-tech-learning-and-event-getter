# Evidence — practices-discovery

本ステージで**誰が何を調べ、何を推論し、本人が何を決めたか**の記録である。支援エージェントの提案が本人の回答に負けた箇所は、黙って落とさず反対意見として残してある。後から「なぜこうなっているのか」を辿る先はここである。

構成:
1. 各参加者が何を見たか
2. インタビューで確定したこと（Q1〜Q13）
3. 反対意見の記録（提案が回答に負けた箇所）
4. 回答が退けなかった支援エージェントの指摘（実践に取り込んだもの）
5. 採らないことを決めたもの
6. 残った不確実性

**greenfield であることを確認した。** コード・設定・履歴から実践を読み取ることはできず、このステージは「発見」ではなく「提案と確認」として進んだ。草案の5節はすべて提案として表示し、確度の低い推論（テスト実行基盤、ロールバック手順、リンタの選択）には確度列で印を付けた。

### 品質（`aidlc-quality-agent`）

スコープの実行ステージ構成（`aidlc-state.md` の Stages to Skip）まで踏み込み、**草案が見ていなかった穴を2つ**見つけた。`user-stories` が SKIP のため受け入れ条件を持つステージが存在せず、`performance-validation` が SKIP のため NFR を実測で確かめるステージが存在しない。リードが C-09 について指摘した「確定させる場所が宙に浮いている」のと同じ種類の穴である。

加えて、**カバレッジ 80% の根拠を検証した**。`org.md` が 80% を課すスコープ名の列挙（`mvp`, `enterprise`, `feature`, `infra`, `classic`）に `greenfield-scraper-mvp` は含まれていない。したがって草案の「`org.md` が課している既定の下限」は誤りで、リードの推論だった。この事実はインタビューの冒頭に「先に確認した事実」として提示し、本人が知ったうえで判断できるようにした。

フィクスチャの出どころ（[S6] = サードパーティ製 Go クライアントのモデル定義）が未検証であることから、「テストは緑のまま本番だけが壊れる」偽の緑の危険を指摘した。

### 開発（`aidlc-developer-agent`）

**R-03 への対応が草案の書き方では成立しない**ことを指摘した。呼び出しだけを閉じ込めても、API が返した JSON の形がそのままモジュールの外へ出れば仕様変更の影響は全体に及ぶ。実際に守るのは型の境界であって fetch の位置ではない。

**API レスポンスの実行時検証が3ファイルのどこにも出てこない**ことを指摘した。これが本ステージで見つかった最も実害の大きい欠落である。TypeScript の型注釈はコンパイル時に消えるため、検証がなければ仕様変更は「型エラー」ではなく「`undefined` が静かに D1 へ書き込まれる」形で現れ、S-05 が検知できない。

事実の指摘を1件。**`.gitignore` に `.dev.vars` が入っていない**（`*.local` は一致しない）。`wrangler dev` を動かした時点で実キーが平文で置かれるため、C-03 がリポジトリの仕組みとして担保されていない。これは提案ではなく、いま確認できる事実である。

構成の分岐（Worker 1つで完結させる案A / Worker と Pages を分ける案B）が、草案では選択肢ではなく前提として書かれていることも指摘した。

### セキュリティ（`aidlc-devsecops-agent`）

**このプロジェクトで実際に効く統制は3つしかない**と判断した。(1) シークレットをリポジトリに入れない仕組み、(2) 第三者由来の文字列を出力するときのエスケープ、(3) ランタイム依存を増やさないこと。

**最も危ない抜け穴としてフィクスチャの作り方を挙げた。** 草案は「フィクスチャで与える」としながら、その作り方に制約を置いていなかった。キー発行後に実レスポンスをそのまま保存してコミットするのは自然な手順だが、公開リポジトリならそこに含まれる主催者名が Git 履歴に恒久的に残る。

C-14 の規則が「保存または表示」しか禁じておらず、**ログ出力という第3の経路が空いている**ことも指摘した。

また、connpass API キーは申請と審査を経て1つだけ発行され（C-02）、**漏洩しても自分でローテーションできない**ことを重視した。一般的な「漏れたら再発行すればよい」が成立せず、R-01 と同じ場所に戻される可能性がある。

### 回答が作り出した3つの帰結

答えそのものには書かれていないが、**答えの組み合わせから必然的に生じる**もの。artifacts に明記した。

1. **公開リポジトリ（Q1=A）× CI デプロイ（Q7=B）** — Cloudflare の API トークンが、公開リポジトリの GitHub Actions シークレットに置かれる。これが本プロジェクト唯一の実質的な外部への露出である。フォーク PR からそこに到達する経路を塞ぐこと（`pull_request_target` を使わない、`on: push` の `main` のみ、スコープ付きトークン、第三者 Action の SHA ピン留め）は好みではなく必須の設定になった
2. **7日ルール（Q11=B）は道具の設定であって習慣ではない** — 人が覚えている規約は急いでいるときに破られる。Renovate の `minimumReleaseAge` か Dependabot の `cooldown` で機械的に強制する
3. **Worker / Pages の分離（Q8=B）は共有する型の置き場所を構造上の判断にする** — Q13 の「フロントとバックで同一の型は共通化する」が、この分離によって単なる好みではなく設計上の必須事項になった

### Q10 の選定根拠（記録）

oxlint の型認識リントは 2026年7月に安定版となり、typescript-eslint の型認識ルール 61 件のうち 59 件をカバーする。Oxfmt は 2026年2月にベータとなり、JavaScript / TypeScript について Prettier と 100% の整形一致を達成している。oxlint と同じツールチェインであり、設定と依存を1系統にまとめられる。

**Oxfmt がベータであることは承知のうえで採用した。整形の選択は覆すのが安いからである**（コードの意味を変えず、`git diff` 1回で戻せる）。リントの選択とは可逆性が違うため、同じ基準で判断していない。

|---|---|
| **DAST**（OWASP ZAP 等） | ログインなし、フォームなし、ユーザ入力由来の書き込みなし。出てくるのはレスポンスヘッダの指摘くらいで、`_headers` の設定で先に片づく。代わりに C-13 / C-14 の固定回帰テスト2本を置く |
| **本格的な SAST**（Semgrep フルルールセット、SonarQube 等） | 数百〜千行規模、単独保守、認証もユーザ入力もない TypeScript アプリでは、誤検知の仕分けコストが検出価値を上回る。CodeQL は公開リポジトリなら無料なので有効化してよいが、**ゲートにはしない** |
| **`eslint-plugin-security`** | Node.js のファイル I/O・子プロセス・正規表現 DoS が主な対象で、`fetch` と D1 しか触らない Workers ランタイムではほぼ空振りする。同じ労力なら `strict: true` のほうが実際のバグを捕まえる |
| **SBOM の生成、成果物への署名、SLSA プロベナンス** | 本件の成果物を消費する第三者が存在しない。作っても誰も検証しない |
| **脅威モデル文書** | 攻撃面が「第三者由来の文字列の出力」1点に集約されており、文書化しても内容が1行にしかならない |
| **負荷テスト・オートスケーリング検証** | 利用者は本人1名、収集は1時間に1回（D-38）、公開ページは保存済みデータを読むだけ（D-34）。無料枠（C-09）の上限にも遠い |
| **B-06 を見越した「情報源プラグイン機構」** | 対象サイトが未特定である以上、根拠のない抽象化になる。ただし**ただ同然で前方互換にできる判断**（プロジェクト側の型に connpass 固有の語彙を持ち込まない、D1 のイベント行に収集元の列を持たせる）は Domain Design へ申し送る |
| **`npm audit` をマージのブロック条件にすること** | ゼロ実行時依存に近い構成で `audit` をゲートにすると、開発時依存の到達不能な脆弱性でマージが止まり、閾値をいじって黙らせる習慣がつく。それは統制の劣化である |

### 手元で解消すべきもの

- **GitHub リポジトリがまだ存在しない**（`git remote -v` が空）。作成とブランチ保護の設定はセットアップ完了後に行う予定。それまで PR ゲート・シークレットスキャン・CI のいずれも動かない
- **`.gitignore` に `.dev.vars` と `.wrangler/` がない。** 骨格 Bolt の実装前に対応する
- **Cloudflare のスコープ付き API トークンが未発行。** CI からのデプロイを組む時点で必要になる

### このステージでは解消できないもの

- **connpass API キーの未発行（C-02、R-01）** — 実データでの検証は、テスト・骨格・デプロイ後確認のいずれについても、手順を設計できても実行して確かめることはできない。確定した実践はすべて「キーがない状態で成立する」ことを前提に組んである
- **フィクスチャの正しさ** — 出どころ [S6] はサードパーティ製クライアントのモデル定義であり、公式リファレンスで検証されていない。境界での厳格なパース（想定外の形なら保存せず失敗として記録する）が、この未検証性に対する唯一の防御である

### 聞かなかったこと

- **公開ページにアクセス解析を入れる予定があるか**（セキュリティ S6）。現時点の前提は「閲覧者の個人データを一切集めない」。入れる場合はその前提が変わるため、判断する時点で記録する
