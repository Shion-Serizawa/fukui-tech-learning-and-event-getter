## Contribution

担当範囲は命名・層の境界・エラー処理・ファイル構成・コードスタイル規約である。

### 1. 層の境界 — R-03 への対応が、草案の書き方では成立しない

これが本レビューで最も重い指摘である。

`discovered-rules.md` の Mandated に「ALWAYS connpass API を呼び出すコードは単一のモジュールに閉じ込め、他のコードはそのモジュールを介してのみ外部データに触れる」とある。R-03（API の仕様変更で収集が止まる）への対応方針としては**不十分**である。呼び出し「だけ」を閉じ込めても、API が返した JSON の形がそのままモジュールの外へ出ていけば、仕様変更の影響範囲は結局コードベース全体に広がる。`started_at` が `start_datetime` に改名されたとき、直す場所が1か所で済むかどうかを決めるのは、fetch の位置ではなく**型の境界**である。

規則は次の3点に分けて書き直すことを提案する。

1. connpass への HTTP 呼び出し（`fetch`、`X-API-Key` ヘッダ、レート制限の待ち、429 の扱い）は単一モジュールに閉じ込める
2. connpass のレスポンス形状をそのまま写した型（DTO）は**そのモジュールの外へ出さない**。外へ出るのは、このプロジェクトが自分で定義したイベントの型だけである
3. DTO からプロジェクト側の型への変換関数を1つ置き、そこを唯一の変換点とする

R-03 で実際に守られるのは 2 と 3 であって、1 ではない。1 だけを規則にすると、規則を守ったまま R-03 に無防備な設計が書ける。

**併せて必要な指摘**: 草案のどこにも、**API レスポンスを実行時に検証する**という話が出てこない。TypeScript の型注釈はコンパイル時に消えるため、`await res.json() as ConnpassEvent[]` と書いた瞬間、仕様変更は「型エラー」ではなく「`undefined` が静かに D1 へ書き込まれる」形で現れる。R-03 を「気づける」状態にするには、変換点で実行時検証を行い、想定外の形を受け取ったら**保存せずに失敗として記録する**必要がある。これは B-05（収集の健全性）が機能するための前提でもある。検証手段（zod / valibot のようなスキーマ検証ライブラリか、手書きの型ガードか）は本人が選ぶ話だが、Workers の無料枠ではバンドルサイズが効いてくるため、手書きガードも現実的な選択肢であることは添えておきたい。

### 2. 層の境界 — API 以外にも境界は要る

草案の Code Style 節は「構造に関する唯一の縛り」と書いているが、少なくともあと2つ必要である。

- **D1 アクセス**: SQL を書く場所を保存モジュールに限定する。Cron ハンドラ、公開ページのレンダリング、RSS 生成のいずれにも `env.DB.prepare(...)` を直接書かない。理由は R-03 と同型で、B-02 の重複排除キー（未確定、Domain Design 待ち）が変わったときに直す場所を1か所にするためである
- **環境バインディングの受け渡し**: Cloudflare Workers には Node のようなプロセスグローバルな環境変数がなく、`env` はハンドラの引数として渡ってくる。したがって「モジュールのトップレベルで秘密情報を読む」書き方は成立しない。`env` を明示的に引数で渡す形に統一する。これは C-03 の実装上の帰結であると同時に、**Testing Posture 側の前提でもある**（`env` を引数で受ける設計でなければ、フィクスチャによるテストが書けない）。リードにはこの点を Testing Posture 節と相互参照しておくことを勧める

### 3. B-06 を見越した境界 — 今決めるべきこと・決めるべきでないこと

B-06（収集元の追加）は Should だが、対象サイトが未特定である。ここで「情報源プラグイン機構」を先に作るのは、対象が分からない以上、根拠のない抽象化になる。**作らないことを提案する。**

一方で、**ただ同然で前方互換にできる判断が2つある**。

- プロジェクト側のイベント型に connpass 固有の語彙（`series`、`event_id` など）を持ち込まない
- D1 のイベント行に「どの収集元から来たか」を示す列を最初から持たせ、一意キーを（収集元, 収集元でのID）の組にする

後者は B-02 の重複排除キーの話と直結するため、**Domain Design の未確定事項（重複排除の判定基準）に「収集元を含めるか」を明示的に足してもらいたい**。後から列を足すのは D1 のマイグレーションで可能だが、一意制約の変更は既存行の作り直しを伴うため、後回しのコストが非対称である。

### 4. エラー処理 — 草案はほぼ空白

`org.md` の構成フェーズのガードレールは「統合境界では常にエラー処理を入れる」「沈黙した失敗は認めない」と述べているが、草案は 429 の扱いに触れるだけである。本プロジェクトの統合境界は connpass API・D1・Cron 起動の3つあり、それぞれ決めるべきことが違う。以下はインタビューで本人が決める必要がある。

- **3県の部分的失敗**: 福井・石川・富山を別々に取得する（C-10）以上、1県が失敗して2県が成功する状態が起きる。成功分を保存して続行するか、全体を中止するか。続行する場合、B-05 は「完全な失敗」と「部分的な失敗」を区別できなければならない
- **Cron 実行の結果記録**: Cron Trigger の失敗は、記録しない限り誰にも見えない。「最後に成功した収集の日時」を D1 に持つことは B-05 の前提であり、これは observability の話である前に**収集コードのエラー処理の一部**である。草案の Deployment 節にある「最終収集日時が表示される」という確認は、この記録があって初めて成立する
- **再試行の方針**: 429 と 5xx をその場で待って再試行するか、その回はあきらめて次の Cron 起動に任せるか。無料枠の Worker には実行時間の上限があり（具体値は C-09 と同様に未確定）、長い待ちは取れない。**「次の起動に任せる」ほうが構造的に無理がない**が、これは収集間隔（未確定、NFR Requirements 待ち）とセットで決まる
- **表示側の失敗**: D1 の読み取りに失敗したとき、空の一覧を返してはならない。「イベントが0件」と「取得に失敗」が利用者に同じ見え方をすると、成功指標（巡回しなくてよい状態）が静かに壊れる。これは利用者に見える正しさの問題であり、規則として書く価値がある
- **エラーの表現方法**: 例外を投げるか、判別可能な戻り値（`Result` 型など）にするか。提案としては「プログラムの誤りは例外、connpass 境界で**起こると分かっている**結果（429 / 該当なし / 形式不一致）は戻り値で表す」。ただしこれは完全に発明であり、本人の好みで決めてよい

C-03 の実装上の帰結もひとつ足したい。**エラーログにリクエストヘッダをそのまま出力しない。** `X-API-Key` を含んだヘッダを丸ごとログに吐くのは、秘密情報をログに書かない規則の最もありふれた破り方である。

### 5. 命名 — 決めるべきは1点に絞れる

言語慣習（変数・関数は camelCase、型は PascalCase）は草案のとおりで争点がない。実際に決めるべきなのは**表記が異なる3つの世界の変換点**である。

- connpass API は snake_case を返す
- D1 は SQLite であり、列名は snake_case が自然である
- TypeScript 側は camelCase である

提案は「変換点は2か所だけ（connpass DTO → プロジェクト型、プロジェクト型 → D1 行）であり、それ以外の場所に snake_case の識別子を出さない」。これは §1・§2 の境界と同じ線であり、別の規則を増やす話ではない。

その他の命名で決めておくと後で揉めないもの:

- ソースファイル名を kebab-case にするか camelCase にするか（純粋に好み。リンタ設定で一度決めて、以後議論しない）
- `wrangler` のバインディング名とシークレット名（`CONNPASS_API_KEY` など）は SCREAMING_SNAKE。**名前は設定ファイルに書いてよい。C-03 が禁じているのは値である** — 草案の Forbidden が「設定ファイルに書かない」と書いているので、値と名前の区別を一言添えたほうが実装時に迷わない

### 6. ファイル構成 — 先に決めるべき architecture の分岐がひとつある

草案の Deployment 節は「Worker（収集・RSS）＋ Cloudflare Pages（公開ページ）」を前提にしているが、**これは構成の分岐であって既定ではない**。少なくとも2案あり、ファイル構成もデプロイ手順も変わる。

- **案A**: Worker 1つ（Cron + RSS ルート + 公開ページのレスポンス）＋ Pages は使わないか静的資産のみ
- **案B**: Pages（公開ページ）＋ Pages Functions（RSS）＋ Worker（Cron 収集）

案Aはデプロイ先が1つで済み、無料枠の消費も追いやすい。案Bは公開ページを静的に配れる。**どちらも成立するため、インタビューで決める項目として立てるべきである。** 草案は案Bを前提として書かれているが、その旨も選択であることも明示されていない。

構成の提案（発明であることを再度断る）:

```
migrations/          D1 マイグレーション（wrangler d1 migrations の命名規約に従う）
src/
  env.ts             バインディングの型定義
  connpass/          §1 の境界。HTTP 呼び出し・DTO・変換関数・実行時検証
  domain/            プロジェクト側のイベント型と、対象判定などの純粋な関数
  storage/           D1 アクセス。SQL はここだけ
  collect/           Cron ハンドラ。上3つを組み立てる
  feed/              RSS 生成
  web/               公開一覧
```

`domain/` を純粋な関数だけの層にしておくと、対象判定・重複排除・福井優先の並びといった「間違えると成功指標に直接響く」ロジックが、Workers ランタイムなしでテストできる。これはカバレッジ 80%（Testing Posture 節）を現実的な線にする効果もある。**Workers のエントリポイント（`scheduled` / `fetch`）を厚く書くほど、カバレッジ下限は苦しくなる。** リードにはこの因果をテスト節にも書いておくことを勧める。

テストの置き場所（実装の隣か `test/` 配下か）はどちらでもよいが、片方に決める。

### 7. コードスタイル — 草案への補足

- `strict: true` に賛成。追加で `noUncheckedIndexedAccess` を勧める（配列アクセスの結果を `undefined` 込みで扱う）。API レスポンスの配列を扱う本プロジェクトでは効き目がある。ただし記述量は増えるので、**本人が選ぶ項目**として出すべきで、既定として押し付けない
- 「`any` を新規に増やさない」より一段具体的に: 外部から来た値は `unknown` として受け、検証を通してから型をつける。§1 の実行時検証と同じことを、スタイルの言葉で言い直したものである
- Prettier + ESLint と Biome の選択は好みの範囲という草案の判断に同意する。付け加える事実は1つだけ: Biome は整形と検査を1つの設定・1つの依存で賄えるため、単独開発で設定の維持コストを抑えたい場合に有利である。それ以上の差は本プロジェクトの規模では出ない
- **`.gitignore` に `.dev.vars` が入っていない。** Cloudflare のローカル開発は `.dev.vars` に秘密情報を置く慣習であり、現状の `.gitignore`（AI-DLC のブロックのみ）はこれを無視しない。`*.local` はあるが `.dev.vars` は一致しない。C-03 の実効性に直結するため、**最初のコード Bolt で必ず追加する**こと。これは意見ではなく、いま確認できる事実である
