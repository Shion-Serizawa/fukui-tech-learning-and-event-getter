| 欠落 | 何が起きるか | 提案する引き取り先 |
|---|---|---|
| `user-stories`（2.4）が SKIP | 受け入れ条件（Given/When/Then）を持つステージが存在しない。テストは「受け入れ条件を検証するもの」だが、検証すべき受け入れ条件がどこにも書かれない | `requirements-analysis`（2.2）が各要件に**合否の判定条件**を必ず添える。inception フェーズのガードレール「Requirements must be testable and verifiable」がすでにこれを要求している。リードはこの要求を `team-practices.md` に明文化しておくべき |

### 2. カバレッジ 80% について（リードの既定値持ち込みを、さらに一段掘る）

リードは「`org.md` が mvp 相当のスコープに課している既定の下限であり、本スコープもこれに当たる」と書いた。ここは正確にしておきたい。`org.md` の `## Testing Posture` が 80% 行カバレッジを課しているスコープ名は `mvp`, `enterprise`, `feature`, `infra`, `classic` の5つで、**本スコープ `greenfield-scraper-mvp` はこの列挙に含まれていない**。したがって 80% は「`org.md` が課している義務」ではなく「mvp 相当とみなしたリードの推論」である。

この区別は実害を伴う。`org.md` は「Build and Test verifies defined coverage floors and affirmed quality targets; they may not be weakened to make a step pass」と定めており、いったんここで 80% を確定させると、後から「通らないから緩める」ことができない。**プロジェクト固有の根拠を持たない数値を、後で緩められない拘束として採用しようとしている**状態である。リードが正直に既定値と書いたことは評価するが、根拠の強さの表示をもう一段下げるべきだと考える。

そのうえで、数値そのものより**測り方**に問題があると見ている。本アプリのコード量の大半は、D1 への読み書き、HTML/RSS の組み立て、画面の描画といった分岐の少ない直線的なコードになる。行カバレッジはそこで容易に稼げてしまい、逆に**リスクが集中している箇所を通っているかどうかを何も語らない**。リスクは次の7か所に偏っている。

1. connpass API クライアント（429 応答時の挙動、リトライ、1秒1リクエストの遵守）— C-04
2. レスポンスの解釈（`prefecture` による対象判定と取りこぼしの扱い）— C-10、D-11
3. 重複排除の判定
4. 日付境界（「これから開催されるもの」は開催日で判定 / D-40、「直近1〜2週間」の終了イベント / D-19）
5. RSS の認証（無認証アクセスが通らないこと）— C-13、D-17
6. 主催者名を保存も表示もしないこと — C-14、D-12
7. 収集停止の検知（B-05、S-05）— 正常系ではなく異常系でしか通らない経路

**提案（`team-practices.md` の `## Testing Posture` 差し替え案）**:

- カバレッジの下限は**全体の行カバレッジではなく、上記1〜4を含むモジュールに対する分岐カバレッジ**を主たる指標とする。全体行カバレッジは参考値として出すに留めるか、下限を置くとしても低め（例: 60%）にして、主指標を分岐カバレッジ側に置く
- それとは独立に、**規則テスト（上記5〜7）を必須とする**。`discovered-rules.md` の `## Forbidden` に書かれた禁止事項のうちコードで検証できるものには、それを破ったら落ちるテストを1本ずつ対応させる。禁止事項を文章だけで持つと、守られているかどうかを誰も確かめない
- 数値そのものは本人が決める。ただし**主指標を何にするかはこのステージで決める**

### 3. APIキーが無い状態でのテストは「通ること」より「嘘を通さないこと」が難しい

リードの「実 API を叩くテストは書かない／フィクスチャで与える」（推論6）には全面的に同意する。C-01 と C-04 の両面から見て他の選択肢がない。ただし草案は**フィクスチャそのものの正しさ**を問題にしていない。ここが本プロジェクト最大の品質リスクだと考える。

フィクスチャの出どころは `constraint-register.md` の [S6]、すなわち**サードパーティ製 Go クライアントのモデル定義**である。公式リファレンスで検証されたものではない。つまり現状の計画は、「未検証のスキーマで作ったフィクスチャに対してテストを書き、それが緑になったことをもって実装が正しいとみなす」形になっている。実 API のレスポンスが少しでも違えば、**テストは緑のまま本番だけが壊れる**。単に落ちるより悪い。

**提案（`team-practices.md` へ追記）**:

- **境界のパースは「知らない形が来たら落ちる」実装にする。** レスポンスを型に流し込むとき、想定した必須フィールドが欠けていたら黙って `undefined` を通さず、その収集回を失敗として扱い記録する。緩いパースは、フィクスチャが間違っていた場合に失敗を隠す
- **フィクスチャは API クライアントモジュールと同じ場所に置き、そこ以外からは参照しない。** `discovered-rules.md` の ALWAYS「API 呼び出しを単一モジュールに閉じ込める」の自然な帰結であり、キー発行後の差し替え範囲を1か所に限定できる
- **キー発行後にやることを、いま手順として書いておく。** (a) 実レスポンスを1回だけ手で取得する、(b) フィクスチャと突き合わせて差分を潰す、(c) 差分があれば C-04 の数値（1秒1リクエスト）も公式リファレンスで確認して更新する。このチェックリストが無いと、キーが出た日に何を確かめればよいかを思い出す作業から始まることになる
- **キー発行後も、自動テストから実 API を呼ぶことは一切しない。** 例外を認めるとすれば、CI に載せず手で叩く疎通用スクリプト1本のみ。これは本人の判断を仰ぐ（下記インタビュー項目）

### 4. テスト可能性のための実装パターン（`discovered-rules.md` に1件も入っていない）

草案の `discovered-rules.md` は制約から導けるものだけに絞っており、その方針自体は正しい。ただし結果として、**テストを書けるようにするための構造上の縛りが1件も入っていない**。以下2件は「あとから足せない」種類の縛りであり、実装が始まる前に決める価値がある。

**(a) 時刻を直接取得しない**

本アプリのロジックはほぼすべて現在時刻に依存する。Cron Triggers による起動、「これから開催されるもの」の判定（D-40）、「直近1〜2週間に終了したもの」の抽出（D-19）、「収集が止まった」の判定（S-05）、いずれもそうである。実装コードの中で直接現在時刻を読むと、**これらはテストで固定できない**。境界値（開催日当日、ちょうど14日前）を検証する手段が無くなり、そこがまさにバグの出る場所である。

> 提案する規則: ALWAYS 現在時刻はハンドラの境界で1度だけ取得し、以降のロジックへは引数として渡す。ロジックの内部で現在時刻を直接読まない

これは好みではなくテスト可能性の要件だが、`org.md` の既定にも IDEATION の制約にも無い。本人の確認が要る。

**(b) 主催者名を構造として持たない**

C-14 / D-12 は「保存または表示しない」という禁止である。文章の禁止は破られたことに気づけない。**D1 のテーブルに該当する列を作らない**ところまで落とすと、違反が構造的に起こり得なくなる（書き込もうとした時点で失敗する）。加えて、API レスポンスを内部の型へ写す関数に対して「変換後のオブジェクトに主催者由来のフィールドが含まれない」ことを検証するテストを1本置く。これで禁止事項が実行可能な形になる。

> 提案する規則: ALWAYS 主催者名は保存先のスキーマにも内部の型にも列／フィールドとして存在させない（C-14、D-12）

### 5. CI 品質ゲートには、いまのところ「止める仕組み」が無い

草案は `## Testing Posture` と `## Code Style` の両方で「`main` へマージする前に CI で実行する。失敗はマージを止める」と書いている。しかし同じファイルの `## Way of Working` は「レビュー担当者は存在しない。プルリクエストによる他者レビューは行わない。ブランチ保護も設ける相手がいない」と書いている。**この2つは両立しない。** ブランチ保護も PR も無ければ、`main` へ直接 push した時点で CI は後追いで落ちるだけで、何も止めない。「失敗はマージを止める」は現状では願望であって実践ではない。

単独開発でも成立する選択肢は3つある。どれを採るかは本人が決めるべきで、決めずに「マージを止める」とだけ書くのは避けたい。

1. **PR + 必須ステータスチェック** — 他者レビューは無しのまま、PR は立てて CI の成功をマージ条件にする。1人でもブランチ保護は設定できる。止める仕組みとして唯一実効性がある
2. **直接 push + CI は事後通知** — 速いが、ゲートではない。「壊れたまま本番へ出る」ことを許容する形になる。マージで自動デプロイ（草案の `## Deployment`）と組み合わせると、壊れたコードがそのまま公開ページに出る
3. **push 前のローカル実行（pre-push フック等）+ CI は二重確認** — 単独開発では現実的。ただし手元をすり抜ける経路（`--no-verify`）は残る

なお、**2 と自動デプロイの組み合わせは品質面から勧めない。** 止める仕組みが無いまま出口だけ自動化すると、失敗の検知が公開ページの異常になる。1 を採るか、あるいは自動デプロイをやめて手動 `wrangler deploy` にするか、どちらかで揃えるのが筋である。

CI に関して草案が触れていない点をもう2つ挙げる。

- **CI が新しいシークレットを1つ増やす。** 草案の `## Deployment` は connpass API キーと RSS の認証情報を挙げているが、CI からデプロイするなら **Cloudflare の API トークン**が CI 側のシークレットとして必要になる。C-03 の対象に含めて扱うべきで、`discovered-rules.md` の ALWAYS（シークレット管理）はこれを包含する書き方に広げられる
- **リポジトリを公開にするか非公開にするかが未確認。** GitHub Actions の無料枠の効き方が変わる（公開リポジトリなら実質無制限、非公開なら月あたりの上限がある）だけでなく、公開ならフォークからの PR でシークレットがどう扱われるかという話にもなる。C-09 は Cloudflare の無料枠についての制約であって CI のコストを見ていないため、ここは未確認のまま残っている

### 6. 結合テストの範囲が、いまの書き方では実行できない

草案は「『Cron 起動 → API 取得 → D1 保存 → 一覧表示』の経路を1本だけ結合テストとして持つ」としている。この1本は**2つの実行基盤をまたいでいる**。前半（Cron 起動 → API 取得 → D1 保存）は Workers 上で動き、`@cloudflare/vitest-pool-workers` で実行できる。後半の「一覧表示」は Pages 側であり、同じテストプロセスの中には入らない。このまま `code-generation` に渡すと、書けないテストを要求することになる。

**提案する分け方**:

- **結合テスト1**: Cron ハンドラを直接起動 → フィクスチャを返す API クライアント → ローカル D1（Miniflare バインディング）へ保存され、期待した行が入っていること。B-01 + B-02、すなわち骨格 Bolt の範囲とちょうど一致する
- **結合テスト2**: D1 に既知のデータを入れた状態で、一覧のレンダリング関数が期待した並び（福井が先、石川・富山が後 / D-20、終了イベントは下部 / D-24、0件時の文言 / D-26・D-29・D-31）を返すこと。ブラウザを起動しない
- **D1 のマイグレーションはテスト起動時に適用する。** これにより「マイグレーションが適用できる」こと自体が毎回検証される。草案の `## Deployment` は「スキーマ変更は前方互換に限る（列の追加のみ）」と提案しているが、現状それを確かめるテストが1本も無い

- OBJECT: 結合テストを「Cron 起動 → API 取得 → D1 保存 → 一覧表示」の1本とした範囲設定。Workers と Pages の2基盤をまたいでおり単一テストとして実行できない。Workers 側とレンダリング側の2本に分けるべき。
- OBJECT: フィクスチャそのものの正しさが論点になっていない点。出どころ [S6] はサードパーティ製クライアントのモデル定義であり未検証で、緩いパースと組み合わせると「テストは緑のまま本番だけ壊れる」偽の緑を生む。境界での厳格なパースと、キー発行後の突き合わせ手順を実践に含めるべき。
- OBJECT: `user-stories`（2.4）と `performance-validation`（4.6）が SKIP であることに触れていない点。受け入れ条件と NFR 検証の引き取り先が存在せず、リードが C-09 について指摘した「確定させる場所が宙に浮いている」のと同じ穴である。前者は `requirements-analysis`、後者は `build-and-test` と `observability-setup` へ明示的に振り分けるべき。
- OBJECT: `discovered-rules.md` にテスト可能性のための構造上の規則が1件も無い点。少なくとも「現在時刻はハンドラ境界で取得して引数で渡す」と「主催者名をスキーマ・内部型に存在させない」の2件は、あとから足せない種類の縛りであり実装開始前に本人の判断を仰ぐべき。
