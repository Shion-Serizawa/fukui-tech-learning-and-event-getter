**Collaborator:** aidlc-devsecops-agent

## Contribution

担当範囲: リント／フォーマット規則、SAST / DAST、シークレット検出、依存関係スキャン、サプライチェーン管理。

最初に全体の判断を書く。**このプロジェクトで実際に効く統制は3つしかない。** (1) シークレットをリポジトリに入れない仕組み、(2) 第三者由来の文字列（connpass のイベント名・説明）を出力するときのエスケープ、(3) ランタイム依存を増やさないこと。残りの「DevSecOps 一式」——DAST、本格的な SAST、SBOM、署名、脅威モデル文書、ブランチ保護——は本件では過剰であり、導入しないことを積極的に推奨する。以下、根拠つきで分ける。

---

### 1. シークレット検出 — 唯一「必ず入れる」と言える統制

本プロジェクトのシークレットは2つ（connpass API キー、個人用 RSS の認証情報）。単独開発・公開リポジトリ想定という条件では、現実的に起きる事故は外部からの攻撃ではなく**自分がキーをコミットすること**である。

本件には、この事故の代償を普通より重くする事情がある。**connpass API キーは申請と審査を経て1つだけ発行される（C-02）。** 漏洩しても自分でローテーションできない。GitHub にプッシュした時点で、再申請または connpass への連絡が必要になり、R-01（審査が通らない）と同じ場所に戻される可能性がある。一般的な「漏れたら再発行すればよい」が成立しない。したがって、ここに数十分かける価値は明確にある。

具体的に入れるもの:

- **GitHub のシークレットスキャン + プッシュ保護を有効にする。** 無料、設定は画面上のトグル1つ。コミット前ではなくプッシュ時に止まる。connpass API キーはカスタムパターンの対象外なので汎用検出に頼ることになるが、Cloudflare API トークンや汎用の高エントロピー文字列は拾う
- **`gitleaks` を CI で実行し、失敗をマージのブロック条件にする。** 本件の CI ゲートで「ブロックにしてよい」と言えるのはこれとリント・型検査・テストだけである
- **`.gitignore` に `.dev.vars` を必ず入れる。** Wrangler のローカルシークレットファイルであり、`wrangler dev` を動かした時点で実キーが平文で置かれる。本件で最も踏みやすい地雷はここ。`.wrangler/` も除外する
- **`wrangler.toml` の `[vars]` にキーを書かない。** `[vars]` は平文の設定であってシークレットではない。API キーと RSS 認証情報は `wrangler secret put` で登録する（リード草案の Deployment の記述と一致する。ここは異論なし）

### 2. CI とデプロイの資格情報 — リード草案が触れていない穴

リード草案の Deployment は「シークレットはリポジトリにも CI の設定ファイルにも置かない」で終わっているが、**`main` へのマージで自動デプロイするなら、Cloudflare の API トークンが GitHub Actions のシークレットに置かれる。** これは「置かない」で片づく話ではなく、置き場所と権限を決める話である。本件で唯一の実質的なサプライチェーン露出はここにある（ワークフローが呼ぶ第三者 Action は、そのトークンを読める）。

自動デプロイを選ぶ場合に必要なもの:

- Cloudflare の **Global API Key を絶対に使わない。** アカウント全体に及び、失効も面倒。スコープ付き API トークン（Workers Scripts:Edit / D1:Edit / Pages:Edit を対象アカウントに限定）を発行する
- ワークフロー先頭で `permissions: contents: read` を宣言し、`GITHUB_TOKEN` を最小にする
- デプロイジョブは `on: push` の `main` のみで動かす。**公開リポジトリならフォークから PR が来る。** `pull_request` トリガのジョブにシークレットを渡さない（`pull_request_target` を使わない）
- `actions/*` と `cloudflare/wrangler-action` 以外の第三者 Action を使う場合はコミット SHA でピン留めする。使う Action が上の2つだけなら、ピン留めまでは不要と判断してよい

**ここが、リード草案が「運用の好み」として提示したインタビュー項目 (b) の性格を変える。** 手元から `wrangler deploy` を打つ運用を選ぶと、Cloudflare のトークンが GitHub 側に一切存在しなくなり、上の4項目がまるごと不要になる。単独開発・期限なしという条件では、これは十分に現実的な選択である。好みの問題としてではなく、「資格情報を GitHub に置くか置かないか」の判断として本人に提示してほしい。

### 3. 出力エスケープ — 本件で唯一の実在する注入面

公開ページと RSS は、**connpass から来た第三者の文字列（イベント名、説明、開催場所）をそのまま再掲する。** 本システムに入力フォームもログインも存在しないので、攻撃面はここ一点に集約される。

- **HTML**: イベント名等を素の文字列連結で HTML に埋めない。エスケープが既定のテンプレート機構を使うか、エスケープ関数を1つ通す。これはリンタで担保できる類のものではない（手で文字列を組み立てる限り、どのリンタも助けてくれない）ため、規則として明示する価値がある
- **XML / RSS**: 同じ文字列が RSS にも入る。`&` や `<` を含むイベント名は**エスケープ漏れがあると単にフィードが壊れる**ので、実害が出やすい。RSS 生成を自作する場合、エスケープはユニットテストの対象にする（「`&` と `<` と `]]>` を含むタイトルで妥当な XML になること」）
- **決めておくべきこと**: connpass の `description` は HTML を含みうる。これを**そのまま描画するか、プレーンテキストのみ扱うか**を決める必要がある。そのまま描画する設計は、公開ページに第三者由来の HTML を載せることになり、本件で唯一の格納型 XSS 経路になる。**プレーンテキスト化（タグ除去、または `description` を使わず `catch` のみ表示）を推奨する。** サニタイズライブラリを入れるのは、後述の依存予算の観点からも割に合わない
- **安価な後詰め**: Cloudflare Pages の `_headers` ファイルで CSP（`default-src 'self'; script-src 'self'; object-src 'none'; frame-ancestors 'none'`）、`X-Content-Type-Options: nosniff`、`Referrer-Policy: no-referrer` を設定する。10分の作業。上のエスケープを間違えたときの実害を大きく下げる。インラインスクリプトを使わない構成（静的な一覧ページなら容易）にしておけば CSP は厳しくできる

### 4. SAST — 「無料で自動なら入れる、それ以上はやらない」

本格的な SAST（Semgrep のフルルールセット、SonarQube、CodeGuru）は本件では過剰である。数百〜千行規模、単独保守、認証もユーザ入力もない TypeScript アプリに対して、誤検知の仕分けコストが検出価値を上回る。

一方で **GitHub の CodeQL は公開リポジトリなら無料・TypeScript は設定ほぼゼロ**なので、有効化しておく分には損がない。ただし**ゲートにはしない**こと。マージを止める条件にすると、止まった理由が本物かどうかを1人で毎回判断する羽目になる。参考情報として受け取り、うるさければ切る、という扱いでよい。

`eslint-plugin-security` は導入を推奨しない。Node.js のファイル I/O・子プロセス・正規表現 DoS を主な対象としており、Workers ランタイムで `fetch` と D1 しか触らない本件ではほぼ空振りする。**それより `tsconfig.json` の `strict: true`（リード草案の提案に賛成）と `noUncheckedIndexedAccess` のほうが、実際のバグ検出という意味では効く。** 外部 API のレスポンスを扱う以上、「あると仮定したフィールドが無い」が最も起きる失敗であり、型システムでそこを締めるのが本件の実効的な安全策である。

### 5. DAST — 導入しない。代わりに固定のテストを2本

DAST スキャナ（OWASP ZAP 等）の導入は明確に過剰である。ログインなし、フォームなし、ユーザ入力由来の書き込みなし。スキャンして出てくるのはレスポンスヘッダの指摘くらいで、それは §3 の `_headers` で先に片づく。

代わりに、**制約を直接検証する回帰テストを2本**、恒久的に置くことを提案する。スキャナより安く、本件の制約に直接対応している。

- **C-13 の否定テスト**: 認証情報を付けずに RSS のエンドポイントを叩き、200 が返らないこと。C-13 は「守れているはず」で済ませてよい種類の制約ではなく、実装変更で静かに壊れうる。1行のテストで永続的に守れる
- **C-14 のスキーマテスト**: D1 に保存される行・公開ページの出力のいずれにも `owner_nickname` / `owner_display_name` が現れないこと（§7 の allowlist と組み合わせる）

加えて設計上の線引きを1つ。**Worker の公開面は「公開ページ」と「認証付き RSS」の2つだけに保ち、connpass への問い合わせを中継する汎用エンドポイントを作らない。** 作ると、自分の API キーのレート枠（C-04）を他人に使われるうえ、C-06（競合サービスの提供）の議論にも近づく。

### 6. RSS の認証方式（C-13 / A-06）— 実現手段は Functional Design だが、守るべき性質は今決められる

方式選択（URL トークン / HTTP Basic）は Functional Design の担当だが、どちらを選んでも成り立つ規則はこの段階で確定できる。

- トークン方式を選ぶ場合、**128 ビット以上のランダム値**（`crypto.randomUUID()` あるいはランダムバイトの base64url）を使う。エントロピーが十分なら総当たりは成立せず、レート制限やロックアウトの仕組みは一切不要になる。安く済ませる正しいやり方はこれである
- どちらの方式でも、**認証情報をリポジトリ・テストのフィクスチャ・CI ログ・公開ページの HTML に一切書かない。** D-32（公開ページから RSS への導線を置かない）は設計意図の話だが、ここは事故防止の話であり、別に書いておく価値がある
- 照合は前方一致や部分一致ではなく値全体で行い、失敗時は一律 401（または 404）を返す
- 補足: URL トークンは Cloudflare 側のリクエストログや RSS リーダーの履歴にパスごと残る。Basic 認証は資格情報が URL に載らない分わずかに扱いが素直である。ただし A-06 のとおり**リーダーで読めることが最優先**なので、動くほうを選んでよい。ここは安全性が決め手にならない

### 7. C-14 / C-05 を「気をつける」ではなく構造で守る

C-14（主催者名を扱わない）と C-05（申告した目的以外に使わない）は、レビューで守る種類の規則にすると必ず漏れる。**構造で自己強制できる。**

- **API レスポンスから内部モデルへの変換を、使うフィールドを明示列挙する形（allowlist）で書く。** レスポンス全体をスプレッドしたり、そのまま保存したりしない。こうすると `owner_nickname` 等は「うっかり」では入り込めない。D1 のスキーマにもその列を作らない
- **API レスポンスの生データをログに出さない。** これがリード草案の規則で抜けている経路である（後述の OBJECT 1）。エラー時に生 JSON をダンプすると、主催者名が Cloudflare のログに書き出され、C-14 の趣旨を静かに破る。ログに出してよいのは HTTP ステータス、イベント ID、件数、所要時間まで
- **テスト用フィクスチャの作り方に制約をかける。** これは重要なので節を分ける（次項）

### 8. フィクスチャ — リード草案で最も危ない抜け穴

リード草案は「API レスポンスは固定データ（フィクスチャ）で与える」としており、方針としては正しい。しかし**フィクスチャの作り方に制約がない。** API キーが発行された後、実レスポンスをそのまま保存してリポジトリにコミットするのは自然な手順だが、そのファイルには主催者のニックネーム・表示名が含まれる。**公開リポジトリなら、C-14 が「扱わない」と決めた個人データが、Git 履歴に恒久的に残る。** 後から消すには履歴の書き換えが要る。

規則として次を提案する。

- **connpass API の実レスポンスをそのままフィクスチャとしてコミットしない。** フィクスチャは手書きするか、実レスポンスから使用フィールドのみを抜き出し、主催者関連フィールドを削除したうえでコミットする
- 同じ理由で、デバッグ目的で保存した生レスポンスをリポジトリ内に置かない（`fixtures/raw/` のようなディレクトリを作らない）

### 9. 依存関係とサプライチェーン — スキャナより「依存を持たない」ことが効く

Worker のバンドルに入る依存は、**connpass API キーと D1 への接続を持った状態で実行される**コードである。悪意ある更新や侵害された推移的依存が1つ混ざれば、キーと蓄積データがそのまま外に出る。一方で本件の必要機能は、依存をほぼ持たずに書ける。

- HTTP クライアント: Workers の `fetch` で足りる。`axios` 等は不要
- RSS 生成: エスケープ込みで数十行。ライブラリは不要
- D1: バインディングの prepared statement を直接使う。ORM は不要
- HTML: 静的な一覧ページであれば、テンプレート機構なしでも書ける（ただし §3 のエスケープ関数は必ず通す）

したがって提案する規範は **「ランタイム依存はゼロを目標とし、追加するときは理由を書く」**。開発時依存（Vitest、リンタ、Wrangler）は対象外。これは本件では禁欲ではなく、単に必要がないという話である。

そのうえで、安い自動化を2つだけ:

- **Dependabot（または Renovate）を週次・グループ化して有効にする。** 依存木が小さいからこそ成立する。木が大きければ PR が溢れて無視され、かえって有害になる
- **`npm audit` を CI で実行するが、マージのブロック条件にしない。** ゼロ実行時依存に近い構成で `audit` をゲートにすると、開発時依存の到達不能な脆弱性でマージが止まり、閾値をいじって黙らせる習慣がつく。それは統制の劣化である。表示して、見て、判断する

その他:

- ロックファイルをコミットし、CI では `npm ci`（`npm install` ではない）を使う
- SBOM の生成、成果物への署名、SLSA プロベナンスは**導入しない**。本件の成果物を消費する第三者が存在しないため、作っても誰も検証しない

### 10. CI の安全ゲート — 提案する最終形

リード草案の Testing Posture / Code Style で挙がっている CI の内容に、安全側の項目を足した形。**ブロックにするものを絞ること**が要点である。

**マージを止める（ブロック）:**
- `gitleaks`（シークレット検出）
- 型検査（`tsc --noEmit`）
- リント / フォーマット検査
- テスト（カバレッジ下限はリードの提案どおり。ここは担当外）

**表示するだけ（アドバイザリ）:**
- `npm audit`
- CodeQL（公開リポジトリで有効化した場合）

**入れないもの:** DAST、商用/本格 SAST、SBOM、署名、ブランチ保護と必須レビュー（レビューする相手が存在しない。ただしシークレットのプッシュ保護は「レビュー」ではないので別枠で入れる）。

### `discovered-rules.md` への追加提案

リードが統合しやすいよう、規則の形で書く。根拠 ID を添えた。

**`## Mandated` への追加:**

- ALWAYS connpass API のレスポンスから内部モデルへの変換は、使用するフィールドを明示列挙する形で書く。レスポンス全体をそのまま保存・転記しない（C-14、C-05。主催者フィールドが偶発的に混入する経路を構造的に塞ぐため）
- ALWAYS 第三者由来の文字列（イベント名・説明・開催場所）を HTML / XML に出力するときは、エスケープを通す。素の文字列連結で埋め込まない（C-12。公開ページと RSS における唯一の注入面）
- ALWAYS テスト用フィクスチャは、主催者関連フィールドを除去した形でのみリポジトリに置く（C-14。実レスポンスをそのままコミットすると、扱わないと決めた個人データが Git 履歴に恒久的に残る）
- ALWAYS 認証なしで個人用 RSS のエンドポイントを叩いたときに 200 が返らないことを、恒久的な回帰テストとして持つ（C-13）

**`## Forbidden` への追加・修正:**

- NEVER connpass API のレスポンス本文をそのままログに出力する（C-14、C-05。既存の C-14 規則は「保存または表示」しか禁じておらず、ログ出力という第3の経路が空いている）
- NEVER Cloudflare の Global API Key を使う。デプロイに資格情報が必要な場合は、対象アカウントに限定したスコープ付き API トークンを使う（`org.md` 運用フェーズのガードレール、最小権限）
- NEVER 個人用 RSS の認証情報を、リポジトリ・テストのフィクスチャ・CI のログ・公開ページの HTML に書き込む（C-13、C-03。既存の C-03 規則は connpass API キーを主眼に書かれており、RSS 側の認証情報と「フィクスチャ」「CI ログ」という置き場所を明示していない）

**`## Assumptions & Open Questions` への追加:**

- リポジトリが公開か非公開か、ホスティングが GitHub かを確認していない。シークレットスキャン・CodeQL・フォーク PR の扱いはいずれもここに依存する [assumption]
- connpass の `description` が HTML を含む場合の扱い（そのまま描画 / プレーンテキスト化）が未確定 [assumption]
- 自動デプロイを選ぶ場合、Cloudflare の API トークンが CI のシークレットとして存在することになるが、その扱いは未確定 [assumption]

### `team-practices.md` への追加提案

- **Code Style**: `strict: true` の提案に賛成。加えて `noUncheckedIndexedAccess` を提案する（外部 API のレスポンスを扱う本件では、型検査が実質的な安全策になる）。`eslint-plugin-security` は導入しない（Workers ランタイムでは空振りする）
- **Code Style（構造の縛り）**: リードが挙げた「API 呼び出しを単一モジュールに閉じ込める」に加えて、「レスポンスから内部モデルへの変換をフィールド明示列挙で書く」を構造上の縛りとして加える
- **Deployment**: `_headers` による CSP / `X-Content-Type-Options` / `Referrer-Policy` の設定を追加する。自動デプロイを選ぶ場合、§2 の4項目（スコープ付きトークン、`permissions: contents: read`、`push` の `main` のみ、第三者 Action の SHA ピン）を追加する
- **Testing Posture**: 「実 API を叩くテストは書かない」に賛成。フィクスチャの作り方の制約（§8）と、C-13 / C-14 の2本の回帰テスト（§5）を追加する

## Positions

AGREE: 「実 API を叩くテストは書かない、フィクスチャで与える」——C-01 / C-04 に照らして正しく、キー未発行という現実にも合っている。

AGREE: シークレットを `wrangler secret` で登録し、リポジトリにも CI 設定ファイルにも置かない方針。本件で最重要の統制であり、リード草案の書き方で過不足ない。

AGREE: `tsconfig.json` の `strict: true`。本件では、どの安全リンタよりも実効的である。

AGREE: リント・フォーマット検査・型検査をマージ前の CI で実行し、失敗をブロックにすること。ブロックにしてよい数少ない項目のひとつ。

AGREE: 環境をひとつ（本番のみ）にする提案。環境を増やすと Cloudflare の資格情報とシークレットの複製先が増え、無料枠（C-09）以外にも管理面の負担が増える。安全側から見ても環境を分ける理由がない。

AGREE: リンタ／フォーマッタの選択（Prettier + ESLint か Biome か）を本人の好みの範囲とすること。安全上の差はない。

OBJECT: `discovered-rules.md` の C-14 規則が「保存または表示」しか禁じておらず、**ログ出力という経路が空いている**。エラー時に API レスポンスの生 JSON をダンプすれば主催者名が Cloudflare のログに書かれ、規則の趣旨が静かに破れる。動詞を広げるか、専用の Forbidden 規則を足すべき。

OBJECT: `team-practices.md` の Deployment が、**Cloudflare へのデプロイに使う資格情報に一切触れていない**。自動デプロイを選ぶなら API トークンが GitHub のシークレットに置かれ、それが本件で唯一の実質的なサプライチェーン露出になる。「シークレットはリポジトリにも CI 設定にも置かない」では、この資格情報の存在そのものが記述から落ちている。

OBJECT: Deployment のインタビュー項目 (b)（自動デプロイか手打ちか）を**運用の好みとして提示しているが、これは資格情報の置き場所を決める安全上の判断でもある**。好みとして聞くと、本人が判断材料を1つ欠いたまま答えることになる。

OBJECT: Testing Posture の「フィクスチャで与える」に**フィクスチャの作り方の制約がない**。キー発行後に実レスポンスをそのまま保存してコミットするのは自然な手順だが、それは C-14 が扱わないと決めた個人データを（公開リポジトリなら）Git 履歴に恒久的に残す。方針としては正しいだけに、ここが空いているのは危ない。

OBJECT: Code Style の「構造に関する唯一の縛り」という書き方。**レスポンスから内部モデルへの変換をフィールド明示列挙で書くこと**も構造上の縛りとして加えるべきで、これは好みではなく C-14 を人の注意力に頼らず守るための設計統制である。
