# Feasibility Assessment — 北陸ITイベント収集アプリ

上流成果物: `aidlc/spaces/default/intents/260919-fukui-event-collector/ideation/intent-capture/intent-statement.md`（intent-statement）で確定した意図・対象エリア・製品範囲を前提とする。

## 結論

**技術的には実現可能。ただし1点、本人の努力では解消できない前提がある。**

intent-statement が求める「北陸のITイベントを定期収集し、公開ページと RSS で閲覧できる状態」は、connpass 公式 API を用いれば標準機能の範囲で構成できる。都道府県での絞り込みは API が標準でサポートしており、収集・保存・表示のいずれにも技術的な障壁は見当たらない。無料枠の制約（Q5=A）にも収まる。

解消できない前提は **connpass API の利用審査** である。API キーは申請・審査を経て発行され、申請は提出済みだが結果は未着（Q1=A）。審査に通らなければ、この構想は connpass に対して成立しない。代替手段としてのスクレイピングは規約で明確に禁止されているため、迂回路は存在しない。

## 技術的実現性

### 取得（connpass API）

| 項目 | 評価 | 根拠 |
|---|---|---|
| 取得手段 | 公式 API の一択 | スクレイピング・クローリングは利用規約 第7条第1項第17号で禁止（2024年9月1日より明記）[S1][S2] |
| 利用条件 | 個人・コミュニティ向けは無償。申請フォームから利用目的を申請し、審査の上で APIキーを1つ発行 [S3] | 発行まで約1週間との利用報告 [S4] |
| 認証 | `X-API-Key` ヘッダ [S4] | — |
| レート制限 | APIキーあたり 1秒1リクエスト。超過時は HTTP 429 [S4] | 公式ヘルプは「一定時間内での連続アクセス回数に制限あり」とのみ記載 [S3] |
| 地域絞り込み | `prefecture` パラメータで全47都道府県の英字名 + `online` を指定可能 [S5][S6] | 福井・石川・富山をそのまま指定できる |
| ページング | `start`（開始位置）と `count`（1〜100）[S6] | — |
| 並び順 | `order` = 1:更新日時 / 2:開催日時 / 3:新着順 [S6] | — |

1秒1リクエストという制限は、本件の規模（北陸3県のイベント、定期取得）では実質的な制約にならない。3県を順に取得しても数リクエストで完結し、`count` の上限100件と合わせれば1回の収集は数秒で終わる。

### 開催形式（オフライン）の判定

connpass のレスポンスに「オンライン/オフライン」を直接示すフィールドは存在しない [S6]。`event_type` は `participation` / `advertisement` の区別であり、開催形式ではない。

したがって判定は **検索時の `prefecture` 指定に依存する**。福井・石川・富山を指定して取得すれば、`online` として登録されたイベントは結果に含まれない。この方式を採用し、取りこぼしや誤判定は許容することが確定している（Q3=A）。

**この方式の限界**（許容された上での既知の弱点）:
- 主催者が都道府県を正しく設定していない場合、取りこぼす
- ハイブリッド開催（現地 + オンライン）がどちらに登録されているかは主催者次第で、一貫しない
- `address` / `place` / `lat` / `lon` は取得できるので、将来補正が必要になった場合の材料は残る

### 保存・公開（Cloudflare）

構成は TypeScript / Cloudflare で確定している（Q4=A）。

| 用途 | 想定サービス | 無料枠での成立性 |
|---|---|---|
| 定期取得 | Cloudflare Workers + Cron Triggers | 成立する。日次〜数時間ごとの実行は無料枠の範囲 |
| データ保存 | Cloudflare D1 | 成立する。北陸3県のイベント件数は D1 の無料枠に対して十分小さい |
| 公開ページ | Cloudflare Pages | 成立する |
| バックエンド | Cloudflare Workers | 成立する |

具体的なサービス構成・実行間隔・ストレージ設計は後続の設計ステップ（Domain Design、NFR Requirements、Infrastructure Design）で確定する。ここでは「無料枠の制約（Q5=A）と矛盾しない」ことまでを評価対象とした。

### 認証付き RSS の実現性

RSS を認証付きで自分専用にすることが確定している（Q9）。**技術的に実現可能**であり、条件つき回答にあった Discord bot への差し替えは不要と判断した。実現手段は2通りある。

- **推測不能なトークンを URL に埋め込む**（例: `/feed/<ランダム文字列>.xml`）— RSSリーダーの実装に依存せず確実に動作する。厳密な認証ではなく「URL を知らなければ辿り着けない」方式である点は留意が必要
- **HTTP Basic 認証** — 主要な RSS リーダーは対応するが、対応状況はリーダー依存

どちらを採用するかは後続の設計ステップで決める。

## リスク分析

| リスク | 影響 | 評価 |
|---|---|---|
| API 利用審査が通らない | プロジェクトが connpass に対して成立しない。代替の取得手段は規約上存在しない | 最大のリスク。申請は提出済みで結果待ち（Q1=A）。審査基準は公開されていないため、通過可能性は評価できない |
| 公開ページが「競合サービスの提供」に該当すると判断される | 公開ができない、または API 利用を停止される | 申請時に公開ページを作る旨を申告済み（Q10=A）のため、審査結果がそのまま判断となる。申告内容と実装が一致している限り、事後に問題化する可能性は低い |
| API の仕様変更 | 収集が停止する | connpass は 2024年に v1 から v2 へ移行し、認証方式とレート制限を変更した実績がある [S2][S4]。同種の変更が再度起きうる |
| レート制限の数値が想定と異なる | 収集方式の見直しが必要 | 「1秒1リクエスト」は利用報告に基づく値であり、公式ヘルプには具体的な数値が記載されていない [S3][S4]。APIキー発行後にリファレンスで確認が必要 |
| 主催者の都道府県設定漏れによる取りこぼし | 成功指標「収集元サイトを巡回する必要がなくなる」が部分的に達成されない | Q3=A で許容済み。ただし取りこぼしの程度は実データを見るまで不明 |

## Assumptions & Open Questions

- connpass API のレート制限「1秒1リクエスト」は利用報告に基づく値であり、公式ドキュメントで確認していない。APIキー発行後にリファレンスで確認する必要がある [assumption]
- API 利用審査の通過可能性は評価できない。審査基準が公開されていないため [assumption]
- API 利用規約の禁止事項にある「競合サービスの提供」が、イベント情報を集約して公開するサイトに及ぶかどうかは規約上明確でない。申請の審査結果が実質的な判断となる [assumption]
- Cloudflare 無料枠での成立性は、サービスの一般的な無料枠の範囲と本件の想定データ量から判断したものであり、具体的な数値見積りは行っていない。Infrastructure Design で確定する [assumption]
- 収集の実行間隔は未確定。NFR Requirements で確定する [assumption]
- 主催者の都道府県設定漏れによる取りこぼしがどの程度発生するかは、実データを取得するまで不明 [assumption]
- connpass 以外の収集元を将来追加するかどうかは未確定（intent-statement から継続）[assumption]
