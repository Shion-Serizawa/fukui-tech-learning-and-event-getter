## 一行でいうと

**北陸（福井・石川・富山）で開催されるオフラインのITイベントを connpass から定期的に集め、公開ページで一覧でき、新着を個人用 RSS で受け取れて、集まらなくなったら気づける状態にする。**

## 範囲の境界

### 作るもの（In scope — Must have）

最初のバージョンに含める。これらが揃って初めて、成功指標「福井のイベントを探すために収集元サイトを巡回する必要がなくなる」（intent-statement）が成立する。

| ID | 能力 | なぜ必要か | 根拠 |
|---|---|---|---|
| S-01 | connpass から北陸3県のイベントを定期的に収集し、保存する | これがないと何も始まらない。成功指標の前提 | [Q1]=A |
| S-02 | 公開ページで、これから開催されるイベントの一覧を見られる | 「ここを見れば分かる」状態の本体 | [Q1]=B |
| S-03 | 一覧で福井・石川・富山を区別して見分けられる | 福井が主対象であり、他県と混ざると絞り込みの手間が戻る | [Q1]=C、C-11 |
| S-04 | 認証付きの個人用 RSS で新着を受け取れる | 見に行かなくても届く状態。機会損失（見逃し）への対応 | [Q1]=D、C-13 |
| S-05 | 収集が止まったことに自分で気づける | 定期取得は黙って止まる。気づけなければ成功指標が崩れる。具体的な形は後続のステップで決める | [Q9]=A |

### 将来やるもの（Should have）

最初のバージョンには含めないが、作る意思がある。

| ID | 能力 | 根拠 |
|---|---|---|
| S-06 | connpass 以外の収集元を追加する | [Q2]=D |

### 作らないもの（Won't have — this time）

明示的に範囲外とする。後から迷わないための線引きであり、将来の再検討を妨げるものではない。

| 対象 | 根拠 |
|---|---|
| キーワードでの検索 | [Q2] で選択されなかった |
| 開催日・エリアでの絞り込みや並び替え | [Q2] で選択されなかった |
| 終了したイベントを遡って閲覧する機能 | [Q2] で選択されなかった。ただし直近終了分は一覧に出る（下記「見せ方」参照） |
| 利用者登録・ログイン機能 | [Q8]=A |
| イベントへの申込み機能 | [Q8]=B。connpass へ飛ばす |
| お気に入り・参加予定の管理 | [Q8]=C |
| 自分以外への通知（メール配信など） | [Q8]=D。S-04 の RSS は本人専用であり、これに該当しない |
| スマートフォンアプリ | [Q8]=E |

## 見せ方の決定

| 項目 | 決定 | 根拠 |
|---|---|---|
| 表示する期間 | これから開催されるもの + 直近1〜2週間に終了したもの | [Q4]=B |
| エリアの区別 | 福井を先に表示し、石川・富山をその後にまとめて表示する | [Q5]=B、C-11 |
| 詳細度 | 一覧にタイトル・日時・場所のみを出し、詳細は connpass へのリンクで飛ばす | [Q6]=A |
| 主催者名 | 表示しない | C-14 |
| 公開範囲 | 公開ページは一般公開、RSS は認証付きで本人専用 | C-12、C-13 |

「終了したイベントを遡る機能は作らないが、直近1〜2週間の終了分は一覧に出る」という整理である。両者は矛盾しない。前者は遡るための操作手段の話、後者は一覧の既定の対象期間の話である。

## 進め方の決定

### API 審査を待たずに進める

connpass の API キーは未発行で、審査結果を待っている状態である（feasibility RAID: I-01）。**設計から実装まで進め、実データでの確認だけをキー発行後に回す** [Q3]=A。

この判断の帰結として、キー発行までの間は次が確認できない状態が続く:
- 実際のレスポンス内容が仕様の理解どおりか
- 主催者の都道府県設定漏れがどの程度あるか（feasibility R-05）
- レート制限の実際の値（feasibility A-01）

### 作る順番

**リスク先行を基本とし、依存順に積む。** [Q7] は「おまかせ」であったため、以下を提案し確認を得た。

「収集 → 保存 → 表示」と素直に積み上げるが、最初のひと通りで **connpass からの取得を端から端まで通す**ことを優先する。キーが届いた時点で真っ先に実データで検証できる状態にしておく。

理由: このプロジェクトで唯一こちらが評価できない不確実性が connpass 側にある（feasibility R-01、R-03、R-05）。表示を先に作り込んでも、取得が想定どおりでなければ作り直しになる。

具体的な単位分割と順序は Units Generation および Delivery Planning で確定する。

## 従う制約

`constraint-register.md` の C-01〜C-14 すべてに従う。特に本範囲に強く効くもの:

- **C-01** — connpass からの取得は公式 API 経由のみ。スクレイピングは規約違反
- **C-06 / C-07** — 公開ページは API 利用申請で申告済みの目的の範囲に収める
- **C-09** — Cloudflare の無料枠に収める。S-01 の収集頻度と S-05 の検知手段はこの制約の下で設計する
- **C-13** — RSS は認証付き本人専用。一般公開しない
- **C-14** — 主催者名は扱わない

## Assumptions & Open Questions

- S-05「収集が止まったことに気づける」の具体的な手段（何をもって「止まった」と判定し、どこへどう知らせるか）は未確定。NFR Requirements および observability-setup で確定する [assumption]
- S-01 の収集の実行間隔は未確定。NFR Requirements で確定する [assumption]
- S-04 の RSS の認証方式（URL トークン方式か HTTP Basic 認証か）は未確定。Functional Design で確定する [assumption]
- S-04 の RSS に載せる範囲（福井のみか3県すべてか）は未確定 [assumption]
- 「直近1〜2週間」の具体的な日数は未確定。Functional Design で確定する [assumption]
- API 審査が通らなかった場合、S-06 の収集元をどこにするかは未検討（feasibility から継続）[assumption]
- 「これから開催されるもの」の判定に、開催日と申込期限のどちらを使うかは未確定 [assumption]
