## 到達経路は2つある

成功指標「福井のイベントを探すために収集元サイトを巡回する必要がなくなる」（intent-statement）への到達経路は2つあり、どちらも独立して成立する。

```
                    [本人]
                      |
        +-------------+-------------+
        |                           |
        v                           v
   経路A: 見に行く             経路B: 届く
   (W-01 を開く)              (RSS リーダーで受け取る)
        |                           |
        v                           v
  一覧を上から見る            新着として通知される
        |                           |
        +-------------+-------------+
                      |
                      v
            気になるイベントを見つける
                      |
                      v
            タイトルをクリック
                      |
                      v
            [connpass のイベントページ]
                      |
                      v
            申込みは connpass 上で行う
```

経路Aは探索コストの解消、経路Bは機会損失（見逃し）の解消に対応する（intent-statement の Problem Statement が挙げる2つの側面）。

## 経路A: イベントを見に行く

```
Flow: イベントを見に行く
利用者: 本人 / 北陸のITコミュニティの閲覧者
きっかけ: 北陸で参加できるIT勉強会があるか知りたくなったとき

Steps:
  1. W-01 を開く -> ページが表示される
  2. 「福井」の節を上から見る -> これから開催される福井のイベントが日付順に並んでいる
  3. 必要なら「石川・富山」の節も見る -> 石川と富山のイベントが並んでいる。各件に県名バッジが付く
  4. 気になるイベントのタイトルをクリック -> connpass のイベントページへ移動する
  5. 申込みは connpass 上で行う -> 本アプリの範囲外

成功したときに見えるもの: 参加したいイベントの connpass ページが開いている状態
```

この経路には分岐も入力もない。ページを開いて上から見るだけである。検索・絞り込み・並び替えを作らないため（scope-document）、操作は縦スクロールとリンクのクリックに限られる。

**設計上の帰結**: 操作が少ないぶん、並び順と区切りの適切さがそのまま使い勝手になる。福井を先に置くこと（C-11）と、終了したイベントを下部にまとめること（[Q3]=A）は、この経路の中心的な設計判断である。

### 終了したイベントへの到達

「終了したイベント」の節は一覧の最下部にある。直近1〜2週間分のみを表示する（scope-document）。

この節に意図的に降りていく動機は「見逃したものを確認する」ことであり、探索の主目的ではない。そのため上部には置かない。過去を遡る操作手段は作らない（scope-document）ため、この節に並ぶもの以上は辿れない。

## 経路B: 新着が届く

```
Flow: 新着が届く
利用者: 本人のみ
きっかけ: 収集によって新しいイベントが保存されたとき（本人の操作を起点としない）

Steps:
  1. 収集が動き、新しいイベントが保存される -> W-02 のフィードに反映される
  2. 本人の RSS リーダーがフィードを取得する -> 新着として表示される
  3. 本人が新着に気づく -> 内容を見る
  4. 気になれば項目のリンクをクリック -> connpass のイベントページへ移動する
  5. 申込みは connpass 上で行う -> 本アプリの範囲外

成功したときに見えるもの: 開催前に新着イベントを認識できている状態
```

この経路は本人の操作を起点としない。これが機会損失（見逃し）への対応として意味を持つ理由である。

W-02 は認証付き本人専用であり（C-13）、**W-01 から W-02 への導線は置かない**（wireframes.md）。本人は自分の RSS リーダーに直接登録する。

## 収集の健全性に気づく流れ

```
Flow: 収集が止まったことに気づく
利用者: 本人
きっかけ: W-01 を開いたとき（経路Aの中で受動的に起こる）

Steps:
  1. W-01 を開く -> フッターに最終収集日時が表示されている
  2. 日付を見る -> 新しければ収集は動いている。古ければ止まっている可能性がある
```

これは独立した流れではなく、経路Aに埋め込まれた受動的な気づきである。

**この手段だけでは不十分である。** W-01 を開かなければ気づけないため、長期間開かなければ止まっていることに気づけない。画面の外での検知手段は NFR Requirements と observability-setup で確定する（scope-document の S-05）。

「しばらく更新されていない場合に警告を出す」ことは選ばれなかった（[Q4]=A）ため、画面側でできるのは日付の表示までである。

## 初めて訪れた人の流れ

オンボーディングの流れは作らない。利用者登録がなく、操作が縦スクロールとリンクのクリックだけであるため、説明を要する手順が存在しない。

W-01 のヘッダーに一行の説明（「福井・石川・富山で開催されるオフラインのIT勉強会」）を置くことで、何のサイトかは分かる。これ以上の案内は置かない。

## うまくいかないときの流れ

| 状況 | 利用者が見るもの | 回復の道筋 |
|---|---|---|
| 該当期間にイベントが0件 | 「該当する期間に開催されるイベントはありません。」とフッターの最終収集日時 | 収集が動いていることは最終収集日時で分かる。待つ以外にすることはない |
| イベントを表示できない | 「現在イベントを表示できません」のみ。最終収集日時も出ない（同じ保存先から読むため、イベントが読めない状況では日時も読めない） | 本人が原因を調べる。閲覧者にできることはない |
| 収集が止まっている | 最終収集日時が古いまま | 本人が収集の仕組みを確認する。閲覧者には古い情報であることが伝わる |
| connpass 側のページが消えている | リンク先が connpass の404ページになる | 本アプリの範囲外。リンク先の生死は確認しない |

最後の行は意図的な割り切りである。リンク先の生存確認を行うと、connpass への追加のアクセスが必要になり、レート制限（C-04）と規約（C-01）の両面で割に合わない。

## Assumptions & Open Questions

- W-02 の配信範囲（福井のみか3県すべてか）は未確定。経路Bで本人が受け取る件数がこれで変わる [assumption]
- RSS リーダーがフィードを取得する間隔は本人の RSS リーダーの設定に依存し、こちらでは制御できない。開催直前に収集されたイベントは、リーダーの取得が間に合わず見逃す可能性がある [assumption]
- 「これから開催されるもの」の判定に開催日と申込期限のどちらを使うかは未確定。申込期限を使う場合、期限切れだが未開催のイベントがどちらの節に入るかが変わる [assumption]
- 収集の実行間隔は未確定。経路Bで新着に気づくまでの遅れがこれで決まる。NFR Requirements で確定する [assumption]
- 画面の外での検知手段（S-05 の残り）は未確定。NFR Requirements と observability-setup で確定する [assumption]
