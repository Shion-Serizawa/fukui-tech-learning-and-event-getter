## 何を作るのか

**北陸（福井・石川・富山）で開催されるオフラインのITイベントを connpass から1時間ごとに集め、公開ページで一覧でき、新着を個人用 RSS で受け取れて、集まらなくなったら気づける状態にする。**

## 解決する問題

北陸で開催されるIT系イベントの情報が複数のサイトに散らばっており、探すのに手間がかかる。福井開催のものだけを絞り込むことが難しく、気づいたときには申込期限や開催日が過ぎている。探すたびに同じ検索手順を繰り返すこと自体が負担になっている（intent-statement）。

この困りごとは2つの側面を持つ。

- **探索コスト** — 情報が散らばっているために、探すこと自体に手間がかかる
- **機会損失** — 探索が間に合わず、申込期限や開催日を過ぎてから気づく

## 誰のためのものか

主な利用者は本人。自分用のツールとして作るが、サイトとして公開し、北陸のITコミュニティの人が見ても分かる程度には整える（intent-statement、stakeholder-map）。RSS は認証付きで本人専用とする。

決定者は本人のみ。報告先はなく、外部の関係者もいない。

## 成功したと言える状態

| 側面 | 成功条件 | 測り方 |
|---|---|---|
| 探索コストの解消 | 福井のイベントを探すために、connpass 等のサイトを自分で巡回する必要がなくなること | 収集元サイトを直接巡回する回数がゼロになる |
| 機会損失の解消 | 開催日より前に RSS へ配信されたイベントの割合が 100% | 収集対象期間に開催されたイベントのうち、開催日より前に RSS に載ったものの割合 |

機会損失側の指標は本ステージで確定した（[Q2]）。「RSS に配信されれば気づける」という本人の判断を、測れる形に言い換えたものである。この形にすると、見逃しの原因が「RSS に載らなかった（システムの責任）」と「載ったが読まなかった（本人の都合）」に分離でき、前者だけを成功条件として測れる。

1時間ごとの収集であれば、connpass に登録されてから最大1時間で RSS に載る。開催直前に登録されたイベントを除けば達成できる。

## 実現可能性

**技術的には実現可能。ただし1点、本人の努力では解消できない前提がある**（feasibility-assessment）。

### 取得手段は API の一択

connpass は 2024年9月1日より利用規約でスクレイピングを禁止している（第7条第1項第17号）。したがって取得手段は公式 API のみであり、迂回路は存在しない。当初の依頼にあった「スクレイピングなどして収集する」方式は取れない。

API の主要な仕様:

| 項目 | 内容 |
|---|---|
| 利用条件 | 個人・コミュニティ向けは無償。申請フォームから利用目的を申請し、審査の上で APIキーを1つ発行 |
| 認証 | `X-API-Key` ヘッダ |
| レート制限 | APIキーあたり 1秒1リクエスト（超過時 HTTP 429） |
| 地域絞り込み | `prefecture` パラメータで全47都道府県 + `online` を指定可能 |

1時間に1回・3県分の取得は数リクエストで完結するため、レート制限は実質的な制約にならない。

### 解消できない前提

**connpass API の利用審査**。申請は提出済みだが結果は未着。審査に通らなければ、この構想は connpass に対して成立しない。審査基準は公開されておらず、通過可能性を評価できない。

### 技術構成

TypeScript / Cloudflare（Workers + Cron Triggers、D1、Pages）。費用は無料枠の範囲に収める。1時間ごとの収集・北陸3県規模のデータ量は、いずれも無料枠に収まる見込みである。

## 作る範囲

### 最初のバージョン（Must — 5件）

| ID | 能力 |
|---|---|
| S-01 | connpass から北陸3県のイベントを1時間ごとに収集し、保存する |
| S-02 | 公開ページで、これから開催されるイベントの一覧を見られる |
| S-03 | 一覧で福井・石川・富山を区別して見分けられる |
| S-04 | 認証付きの個人用 RSS で新着を受け取れる（3県すべてを配信） |
| S-05 | 収集が止まったことに自分で気づける |

5件すべてが Must なのは、互いを補完して初めて成功指標を満たすためである。S-01・S-02 が前提、S-03・S-04 が「見に行く」「届く」の2経路、S-05 が前提の維持にあたる。

### 将来やること（Should）

- S-06 — connpass 以外の収集元の追加（対象サイトは未特定）

### 作らないもの

キーワード検索、開催日・エリアでの絞り込みや並び替え、過去イベントを遡って閲覧する機能、利用者登録・ログイン、イベントへの申込み機能、お気に入り・参加予定の管理、自分以外への通知、スマートフォンアプリ。

## 画面の構想

画面は2つのみ。

- **W-01 イベント一覧（一般公開）** — ヘッダー →「福井」→「石川・富山」→「終了したイベント」→ フッター（最終収集日時）。1件はカードで、タイトル・日時・場所・（県名バッジ／参加者数／ハッシュタグ）の4行。詳細は connpass へリンクする
- **W-02 個人用 RSS（認証付き本人専用）** — 公開ページからの導線は置かない

表示するのは、これから開催されるもの（開催日で判定）と直近1〜2週間に終了したもの。イベントが0件の期間は「該当する期間に開催されるイベントはありません」と明示する。

## 体制

単独開発。役割分担も報告も存在しない。Team Formation と Market Research は実行ステップから外してある。

作業の順序は、B-01（収集）→ B-02（保存）を最初に端から端まで通し、次に B-05（健全性）、B-03（公開一覧）、B-04（RSS）、最後に B-06（収集元の追加）。connpass からの取得が唯一こちらで評価できない不確実性であるため、そこを先に通す。

## 主なリスク

| ID | リスク | 影響 | 対応方針 |
|---|---|---|---|
| R-01 | API の利用審査が通らない | 致命的。代替手段は規約上存在しない | 受容。**実装が完了して実データ待ちだけになった時点で、代替手段の検討に入る**（[Q1]=C で確定） |
| R-02 | 公開ページが「競合サービスの提供」に該当すると判断される | 大。公開できない、または利用停止 | 低減済み。申請時に公開ページを作る旨を申告済み。申告内容と実装を一致させ続ける |
| R-03 | API の仕様変更により収集が停止する | 中 | 低減。S-05 で検知する。API 呼び出し箇所を1か所に閉じ込める |
| R-05 | 主催者の都道府県設定漏れによる取りこぼし | 中 | 受容。実データで程度を確認する |

R-01 の打ち切り条件を本ステージで確定させた点が、IDEATION 開始時からの主な変化である。従来は「待つ以外にできることがない」としか書けていなかった。

## 進めてよいかの判断

**進めてよい（Go）。** 根拠は3点。

1. **技術的な障壁がない** — 北陸3県の絞り込みは API が標準でサポートしており、収集・保存・表示のいずれにも未解決の技術課題がない
2. **費用と期限の制約に無理がない** — 無料枠に収まり、期限もない
3. **唯一の致命的リスク（R-01）に打ち切り条件がある** — 待ち続ける状態にはならない

R-01 が未解決のまま INCEPTION に入ることは意図的である。API キーがなくても設計と実装は進められ（[Q3]=A of scope-definition）、実データでの確認だけがキー発行後に回る。

## Assumptions & Open Questions

- API 利用審査の通過可能性は評価できない。審査基準が公開されていないため [assumption]
- API 利用規約の「競合サービスの提供」禁止が本件の公開ページに及ぶかは規約上明確でない。審査結果が実質的な判断となる [assumption]
- レート制限「1秒1リクエスト」は利用報告に基づく値であり、公式ドキュメントで未確認 [assumption]
- Cloudflare 無料枠での成立性は一般的な無料枠の範囲と想定データ量からの判断であり、数値見積りは行っていない [assumption]
- 主催者の都道府県設定漏れによる取りこぼしの程度は、実データを取得するまで不明 [assumption]
- R-01 が現実化した場合にどの収集元へ切り替えるかは未検討。打ち切り条件は決めたが、切り替え先は決めていない [assumption]
- 「開催日より前に RSS へ配信された割合が 100%」という成功条件は、開催直前に connpass へ登録されたイベントについては収集間隔（1時間）の分だけ達成できない場合がある [assumption]
