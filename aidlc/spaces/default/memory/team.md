## Way of Working

**コードは GitHub の公開リポジトリに置く**（Q1=A）。リポジトリはひとしきりのセットアップが終わった時点で作成し、あわせてブランチ保護を設定する（Q2=A）。

トランクベース開発。`main` が唯一の長命ブランチで、Bolt ごとに短命の作業ブランチを切り、`main` へ squash-merge して1 Bolt = 1コミットにする。ワークツリーの base も target も `main`。

**`main` への変更は必ず PR を経由し、CI が通らないとマージできない**（Q2=A）。単独開発だが、これは他者レビューのためではない。**止める仕組みを1つ持つため**である。直接 push と自動デプロイを組み合わせると、テストの失敗に気づく場所が公開ページの異常になる。レビュー担当者は存在しないので、承認者を必須にはしない。ゲートは人ではなく CI である。

- 複数 Bolt を同時に進めない。作る順序は B-01（収集）→ B-02（保存）→ B-05（健全性）→ B-03（公開一覧）→ B-04（RSS）→ B-06（収集元追加）の一本道（D-35）
- 環境を分ける場合も長命なリリースブランチは作らない。そもそも環境は本番ひとつである（Q9=A、`## Deployment` 参照）

**公開リポジトリであることの帰結を1つ、ここに書いておく。** 公開リポジトリにはフォークからの PR が来る。CI からデプロイする以上（Q7=B）、Cloudflare の API トークンが GitHub Actions のシークレットとして存在することになる。フォーク PR からそのトークンに到達する経路を塞ぐことは、好みではなく必須の設定である。具体的な統制は `## Deployment` に書いた。

`project.md` に確定済みの規則がひとつある。**AI-DLC のステージが1つ承認されるごとに、そのステージの成果物を Conventional Commits 形式で1コミットにまとめてコミットする。** これはワークフロー成果物（`aidlc/` 配下）に対する規則である。アプリケーションコードのコミットに Conventional Commits を用いるかどうかは縛らない。

## Walking Skeleton

最初に薄い一本（端から端まで動くことだけを確かめる最小版）を通す。有効なスコープ `greenfield-scraper-mvp` が `skeleton: on` を宣言しており、IDEATION の着手順序（D-35）もすでに骨格の形をしている。

骨格 Bolt の中身は **B-01（収集）+ B-02（保存）**。完了条件は **Cloudflare 上で動くところまで**（Q3=A）。すなわち次の3つを実環境で確認して初めて「通った」とする。

1. Cron Triggers による定期実行が Cloudflare 上で走る
2. D1 に行が入る
3. 公開ページにその行が出る

**この完了条件は、Worker と Pages を分ける構成（Q8=B）と CI からの自動デプロイ（Q7=B）を骨格の範囲に引き込む。** 3つ目の確認は Pages 側であり、そこに到達するにはデプロイ経路が両方とも通っている必要がある。これは意図した設計である。骨格 Bolt の目的は「未検証の配管を先に潰す」ことであり、本プロジェクトで未検証なのは connpass からの取得だけでなく、Worker / Pages / D1 / CI の接続そのものだからである。

**connpass API キーは未発行である**（C-02、R-01）。骨格は手で書いたフィクスチャ（`## Testing Posture` 参照）で通し切る。キーが発行された時点で実データに差し替え、次の手順で確認する。

1. 実レスポンスを1回だけ手で取得する（自動テストからは呼ばない）
2. フィクスチャと突き合わせ、差分を潰す
3. 差分があれば C-04 のレート制限の数値も公式リファレンスで確認し、必要なら制約を更新する

骨格 Bolt は単独で走らせ、ゲートを立てる。本人が明示的に承認してから残りの Bolt へ進む。骨格が出荷された後、残りの Bolt を自動で進めるか毎回止めるかを尋ね、その選択を `Construction Autonomy Mode` として記録する。

骨格 Bolt には、実装を始める前に片づける前提作業が1つある。**`.gitignore` に `.dev.vars` と `.wrangler/` を追加すること。** 現状の `.gitignore` は AI-DLC のブロックのみで、`*.local` は `.dev.vars` に一致しない。`wrangler dev` を動かした時点で実キーが平文で置かれるため、C-03 がリポジトリの仕組みとして担保されていない状態にある。

## Testing Posture

- **Methodology**: test-after
- **Ordering**: テスト可能な各レイヤーをまず実装し、そのレイヤーが動く状態になった直後に、同じ Bolt の中でそのレイヤーのテストを書いて実行する。判定ロジックには必ずテストを伴わせる。
- **テスト実行基盤**: Vitest。Cloudflare Workers 側は公式の `@cloudflare/vitest-pool-workers` を用い、実際の Workers ランタイム上で走らせる（要約確認での指摘）
- **カバレッジ**: 行カバレッジ 80%。**対象は Worker 側（収集・保存・RSS）のみとし、Pages 側（公開ページの描画）は対象外とする**（Q5=B、要約確認での指摘）
- **テスト量**: 本ワークフローの `Test Strategy` は `Standard`。スコープの下限は加算的であり、`Standard` の範囲を狭めたり置き換えたりしない

判定ロジックにテストを必ず伴わせるのは、本プロジェクトの正しさが判定に集中しているからである。福井かどうかの判定（C-10、D-11）、重複の排除、「これから開催されるもの」の判定（D-40）、「直近1〜2週間」の抽出（D-19）——いずれも入力と出力がはっきりしており、間違えると成功指標に直接響く。

カバレッジ 80% を Worker 側に限る理由も同じ性質のものである。Pages 側の描画コードは分岐が少なく直線的で、行カバレッジを稼ぐのは容易だが、稼いだところで正しさを何も語らない。80% という数値が意味を持つのは、判定ロジックと外部境界が集まっている Worker 側だけである。

**この 80% は後から緩めない。** `org.md` は「Build and Test verifies defined coverage floors and affirmed quality targets; they may not be weakened to make a step pass」と定めている。下げる判断はこのステージで済ませてある（対象を Worker 側に絞るという形で）。

### フィクスチャ

**テスト用のデータは手で書く。connpass API の実レスポンスをそのままリポジトリに置かない**（Q6=A）。

これは手間の話ではない。実レスポンスには主催者のニックネーム・表示名が含まれる。**公開リポジトリ**（Q1=A）に一度コミットすれば、C-14 が「扱わない」と決めた個人データが Git 履歴に恒久的に残り、消すには履歴の書き換えが要る。デバッグ目的で保存した生レスポンスをリポジトリ内に置くことも同じ理由で行わない。

フィクスチャは connpass の境界モジュールと同じ場所に置き、そこ以外からは参照しない。キー発行後の差し替え範囲を1か所に限定するためである。

**フィクスチャの出どころは公式リファレンスで検証されていない**（[S6] はサードパーティ製 Go クライアントのモデル定義である）。したがって「フィクスチャに対するテストが緑だから実装が正しい」とは言えない。この偽の緑を防ぐため、境界でのパースは**知らない形が来たら落ちる**実装にする（`discovered-rules.md` の `## Mandated` 参照）。想定した必須フィールドが欠けていたら `undefined` を通さず、その収集回を失敗として記録する。

### 実 API を呼ばない

自動テストから connpass API を呼ぶことは、キー発行後も一切しない。C-01（規約）と C-04（レート制限）の両面から成立せず、C-02（キー未発行）で現時点では実行すらできない。

### テストの構成

結合テストは2本に分ける。1本にまとめると Workers と Pages の2基盤をまたぐことになり、単一のテストプロセスでは実行できない。

- **結合テスト1（Worker 側）**: Cron ハンドラを直接起動 → フィクスチャを返す API クライアント → ローカル D1（Miniflare バインディング）に期待した行が入ること。骨格 Bolt の範囲と一致する
- **結合テスト2（描画側）**: D1 に既知のデータを入れた状態で、一覧のレンダリングが期待した並びを返すこと（福井が先・石川富山が後 / D-20、終了イベントは下部 / D-24、0件時の文言 / D-26・D-29・D-31）。ブラウザは起動しない
- **D1 のマイグレーションはテスト起動時に適用する。** これで「マイグレーションが適用できる」こと自体が毎回検証される

**制約を直接検証する回帰テストを2本、恒久的に置く。**

- 認証情報を付けずに個人用 RSS のエンドポイントを叩き、200 が返らないこと（C-13）
- D1 に保存される行にも公開ページの出力にも主催者名が現れないこと（C-14）

この2本は DAST スキャナの代わりである。本システムにはログインもフォームもユーザ入力由来の書き込みもなく、スキャナをかけて出てくるのはレスポンスヘッダの指摘くらいで、それは `_headers` の設定で先に片づく（`## Deployment` 参照）。制約に直接対応した固定テストのほうが安く、実効的である。

RSS の生成を自作する場合、エスケープはユニットテストの対象とする（`&`、`<`、`]]>` を含むタイトルで妥当な XML になること）。エスケープ漏れは単にフィードが壊れるため、実害が出やすい。

### エラー処理をテストできる形にしておく

- **現在時刻はハンドラの境界で1度だけ取得し、以降のロジックへは引数として渡す。** 本アプリのロジックはほぼすべて現在時刻に依存しており、ロジックの内部で直接読むと境界値（開催日当日、ちょうど14日前）を検証する手段がなくなる
- **収集停止の検知（B-05、S-05）は、失敗を意図的に起こせる形で実装する。** 異常系でしか通らない経路であり、テストで通せなければ「書いたが一度も動いたことがない」状態で本番に出る。それは検知の仕組みとしては無いのと同じである
- **「最後に成功した収集の日時」を D1 に記録する。** これは S-05 の前提であると同時に、フッターの最終収集日時（D-25）の出どころでもある

### 検証の引き受け先

計画上、受け入れ条件と性能検証を持つステージが実行対象に入っていない。引き受け先をここで確定させた（Q12=A、計画は変えない）。

| 項目 | 引き受け先 |
|---|---|
| 各機能が「できた」と言える条件（受け入れ条件） | `requirements-analysis` が各要件に合否の判定条件を必ず添える |
| 性能面の検証 | 決定的に検証できるものは `build-and-test` のテストへ、実測でしか分からないものは `observability-setup` の監視項目へ振り分ける。どちらにも載らない目標値を作らない |

**負荷テストは実施しない。** 利用者は本人1名、収集は1時間に1回（D-38）、公開ページは保存済みデータを読むだけ（D-34）であり、Cloudflare 無料枠（C-09）の上限にも遠い。代わりに「レート制限を守っていること」を決定的なユニットテストで担保する。

D-41（開催日より前に RSS へ配信されたイベントの割合が 100%）は成功条件であって単体テストの対象ではない。「配信対象を選ぶロジックが正しいか」は Bolt 内のテストへ、「実際に配信され続けたか」は `observability-setup` の監視項目へ振り分ける。

## Deployment

**構成は Worker と Pages を分ける**（Q8=B）。収集（Cron）と RSS は Worker、公開ページは Pages が担う。

**環境は本番ひとつ**（Q9=A）。`org.md` の既定は「本番へのデプロイは手動承認」だが、その承認はテックリードとプロダクトオーナーの署名を想定した仕組みであり、承認する相手が存在しない。承認ゲートは AI-DLC の Bolt ゲートと PR の CI がすでに担っている。

**デプロイは CI から自動で行う。`main` に入ったら自動デプロイする**（Q7=B）。

### 公開リポジトリ × CI デプロイの帰結

この2つの答え（Q1=A と Q7=B）が組み合わさると、**Cloudflare の API トークンが、公開リポジトリの GitHub Actions シークレットに置かれる**ことになる。これが本プロジェクト唯一の実質的な外部への露出である。以下は好みではなく必須の設定である。

- **Cloudflare の Global API Key を使わない。** スコープ付き API トークン（Workers Scripts:Edit / D1:Edit / Pages:Edit を対象アカウントに限定）を発行する
- **デプロイジョブは `on: push` の `main` のみで動かす。** 公開リポジトリにはフォークから PR が来る
- **`pull_request_target` を使わない。** `pull_request` トリガのジョブにシークレットを渡さない
- ワークフロー先頭で `permissions: contents: read` を宣言し、`GITHUB_TOKEN` を最小にする
- 第三者製の GitHub Action はコミット SHA でピン留めする

### シークレット

- connpass API キーと個人用 RSS の認証情報は `wrangler secret put` で本番へ登録する。`wrangler.toml` の `[vars]` は平文の設定であってシークレットではない
- **名前と値を区別する。** C-03 が禁じているのは値である。バインディング名やシークレット名（`CONNPASS_API_KEY` など）を設定ファイルに書くことは問題ない
- **GitHub のシークレットスキャンとプッシュ保護を有効にする。** 無料で、設定は画面上のトグルである。connpass API キーは申請と審査を経て1つだけ発行され（C-02）、漏洩しても自分でローテーションできない。一般的な「漏れたら再発行すればよい」が成立しないため、ここは安く厚く守る
- `.gitignore` に `.dev.vars` と `.wrangler/` を入れる（現状入っていない。骨格 Bolt で対応）

### CI のゲート

**マージを止めるもの**: `gitleaks`（シークレット検出）、型検査（`tsc --noEmit`）、リント / フォーマット検査、テスト（カバレッジ下限を含む）。

**表示するだけのもの**: `npm audit`、CodeQL（公開リポジトリなら無料。有効化してよいが、ゲートにはしない）。

止めるものを絞るのは意図的である。単独開発でゲートを増やすと、止まった理由が本物かどうかを毎回1人で判断する羽目になり、閾値をいじって黙らせる習慣がつく。それは統制の劣化である。

### 依存関係

**実行時の依存は、ある程度枯れているものであれば入れてよい**（Q11=B）。ただし**公開から7日未満のバージョンは入れない**。サプライチェーン攻撃の多くは公開直後の短い窓で発現するため、そこを避けるだけで費用対効果が高い。

**この7日は心がけではなく道具の設定として強制する。** Renovate の `minimumReleaseAge` か Dependabot の `cooldown` で設定する。人が覚えている規約は、急いでいるときに破られる。

- ロックファイルをコミットし、CI では `npm ci` を使う（`npm install` ではない）
- Dependabot または Renovate を週次・グループ化して有効にする。依存木が小さいからこそ成立する運用である
- SBOM の生成、成果物への署名、SLSA プロベナンスは導入しない。本件の成果物を消費する第三者が存在せず、作っても誰も検証しない

### ロールバックとデプロイ後の確認

- **ロールバック**: Worker は `wrangler rollback`（直前のデプロイへ戻す）、Pages はダッシュボードから以前のデプロイを再公開する
- **D1 のスキーマ変更は前方互換に限る。** 列の追加のみとし、削除・改名は別 Bolt に分ける。コードを戻してもデータが壊れない形を保つ
- **デプロイ後の確認**: 公開ページが 200 を返し、最終収集日時が表示されること（D-25）。Cron の実行は次の起動を待つ必要があるため、デプロイ直後の確認には含めない
- **`_headers` でセキュリティヘッダを設定する**: CSP（`default-src 'self'; script-src 'self'; object-src 'none'; frame-ancestors 'none'`）、`X-Content-Type-Options: nosniff`、`Referrer-Policy: no-referrer`。インラインスクリプトを使わない構成にしておけば CSP は厳しくできる

## Code Style

**リンタは oxlint（型認識によるリントを有効にする）、フォーマッタは Oxfmt を使う。**

選定の根拠を記録しておく。oxlint の型認識リントは 2026年7月に安定版となり、typescript-eslint の型認識ルール 61 件のうち 59 件をカバーする。Oxfmt は 2026年2月にベータとなり、JavaScript / TypeScript について Prettier と 100% の整形一致を達成している。oxlint と同じツールチェインであり、設定と依存を1系統にまとめられる。Oxfmt がベータであることは承知のうえで採用した。**整形の選択は覆すのが安い**（コードの意味を変えず、`git diff` 1回で戻せる）ためである。リントの選択とは可逆性が違う。

**リントは厳しめにする**（Q13）。AI による支援を前提に書くため、機械が見られる部分は機械に厳しく見させる方針である。

- **言語**: TypeScript。`tsconfig.json` の `strict: true` を有効にする
- **外部から来た値は `unknown` として受け、検証を通してから型をつける。** 「`any` を増やさない」より一段具体的な言い方であり、実行時検証（`discovered-rules.md` 参照）をスタイルの言葉で言い直したものである
- **命名**: TypeScript の慣習に従う（変数・関数は camelCase、型・クラスは PascalCase）。snake_case の識別子は2つの変換点（connpass DTO → プロジェクト型、プロジェクト型 → D1 行）の内側にのみ置き、それ以外の場所に出さない。バインディング名・シークレット名は SCREAMING_SNAKE
- ソースファイル名の表記とテストの置き場所は、リンタ設定で一度決めて以後議論しない
- `eslint-plugin-security` は導入しない。Node.js のファイル I/O・子プロセス・正規表現 DoS を主な対象としており、`fetch` と D1 しか触らない Workers ランタイムではほぼ空振りする。同じ労力なら `strict: true` のほうが実際のバグを捕まえる

**構造の規約はこの節に置かない。** 層の境界、型の境界、共有する型の置き場所といった規約は `discovered-rules.md` の `## Mandated` にある。この節は承認後 `team.md` の `## Code Style` へ昇格し、整形・命名の規約として読まれる場所になるため、構造の話を同居させると昇格後の読み手が混乱する。
